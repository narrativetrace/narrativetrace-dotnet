# NarrativeTrace 示例

[English](README.md) | [Español](LEAME.md) | **简体中文**

一组可运行的教程，展示 NarrativeTrace 在实践中的样子。这些项目**不发布**——它们的存在
是为了让开发者(或 AI 代理)能运行一个真实的场景，读取生成的追踪，并把它和产生它的代码
对应起来。

请把这些项目当作有推荐顺序的教程，而不是可复用的 API。每个示例的入口类在其 XML 文档中
带有引导式阅读顺序；深入某个示例时从那里开始。

## 项目一览

| 项目 | 语言 | 入口 | 教什么 |
|---|---|---|---|
| `NarrativeTrace.Examples.ECommerce` | C# | `ECommerceDemo` | 旗舰示例：追踪一个真实的服务调用图——用 `AddNarrativeTracing` 接线容器、`[Narrated]` / `[OnError]` / `[NotTraced]`、异步完成汇入同一条追踪、fork-join(分叉汇合)与即发即弃分组、成功与失败场景。 |
| `NarrativeTrace.Examples.Clarity` | C# | `ClarityExample` | 清晰度子系统如何为命名质量打分：一个酒店预订领域，名字刻意分为优秀、尚可和糟糕三档。 |
| `NarrativeTrace.Examples.Minecraft` | C# | `MinecraftExample` | 仅靠命名能让追踪质量改变多少：同一行为追踪两次，一次用领域专属命名，一次用泛化命名。 |
| `NarrativeTrace.Examples.Library` | F# | `LibraryExample` | 在 F# 中使用 NarrativeTrace：在一个小型图书借阅领域里，通过 `DispatchProxy` 从 F# 接口追踪 F# 服务。 |
| `NarrativeTrace.Examples.Common` | C# | *(类库，无入口)* | 示例共享工具：`DemoRun` 驱动器、各次运行用来写日志的 `ConsoleLoggerFactory`、把追踪事件变成实时 `→ ← !!` 行的 `NarrationStreamListener`，以及段落标记。 |

每个示例项目都**没有 NuGet 依赖**——只有对 `src/` 下类库的项目引用。示例在 `tests/`
下有自己的测试项目(`NarrativeTrace.Examples.*.Tests`)，固定每次运行的形状。

## 运行示例

每个示例都是普通的控制台项目：

```bash
dotnet run --project examples/NarrativeTrace.Examples.ECommerce
dotnet run --project examples/NarrativeTrace.Examples.Clarity
dotnet run --project examples/NarrativeTrace.Examples.Minecraft
dotnet run --project examples/NarrativeTrace.Examples.Library

./build.sh RunExamples   # 依次运行全部四个
```

示例唯一接受的开关是 `--classic`(放在 `--` 之后)：此时每一行都带上传统的时间戳 / 级别 /
`[thread]` / `[traceId]` / `[logger]` 前缀，而不是只有消息本身。节奏和颜色是启动器的事，
不是示例的事。

## 演示启动器

仓库根目录附带 `./demo.sh`——观看示例的最快方式：一条命令，没有构建噪音，实时叙述按调用
深度着色并缩进，每种渲染都作为独立段落宣告。`./demo.sh` 打开交互式选择器；
`--example <名称>` 非交互地运行；`--list` 列出示例；
`./build.sh Demo --example <名称> --no-pause` 从构建中运行同样的内容。

**它是一步步走的，不是一滚而过。** 在终端上，演示在每个场景之后停下——`[回车]` 继续，
`q` 退出——每个场景开头都有一段说明，讲*该场景的追踪是如何配置的*：这里是容器上的
`AddNarrativeTracing`，那里是一个直接的 `NarrativeTraceProxy.Create`，`[Narrated]` /
`[OnError]` / `[NotTraced]` 中的哪一个产生了你即将读到的内容。这些说明放在
`examples/demo/wiring.awk` 里，以场景标题为键；`DemoWiringCheck` 构建目标(同时也是
`tests/BuildScript.Tests` 中的一个测试，因此随测试套件一起运行)会在某个场景失去说明、或
某条说明的场景已不存在时让构建失败。带停顿的运行先完整录制再逐段回放，所以停顿永远不会
夸大追踪树报告的耗时；`--no-pause` 实时一口气播完，管道和 CI 得到的就是这个。

**渲染从哪里来**每次运行只回答一次，在第一个渲染段落处，因为这是每个观众接下来都会问的
问题。没有默认渲染器，也没有任何东西要配置：捕获产生一个 `TraceTree`，你调用想要的渲染器
(`IndentedTextRenderer.Render(trace)`)；渲染器都是静态的 `Render(TraceTree)` 方法，所以
你自己的渲染器就是任何一个从树到字符串的函数。实时的 `→ ← !!` 行根本不是渲染器——那是
`DualPathPipeline` 上的一个监听器(`Examples.Common` 中的 `NarrationStreamListener`，
Java `Slf4jTraceEventListener` 的 `ILogger` 孪生)，是唯一不需要写任何渲染代码的视图。
配置只在一个地方选择渲染器，即从测试写出的追踪文件：`NARRATIVETRACE_OUTPUT=true` 加上
`NARRATIVETRACE_FORMAT=markdown|text|mermaid|plantuml`，其中 `markdown` 是默认值，
`NarrativeTrace.MSBuild` 包的 `NarrativeTraceOutput` / `NarrativeTraceFormat` 属性设置的
是同样的开关。每个段落标记都写明了产生它的渲染器。

**经典日志输出是一等公民。** 叙述就是普通的 `ILogger` 流量，经由普通的日志提供程序，
因此它可以按任何日志工具都能摄取的传统格式呈现——完整的 `yyyy-MM-dd HH:mm:ss.fff`
时间戳、级别、线程、每个场景一个 `traceId` 作用域，以及 logger 名称。三个地方可以看到它：

- `./demo.sh --example <名称> --classic`——整个运行，原样呈现。
- ecommerce 演示在运行中途把一个场景("Unknown Customer")以经典形式内联展示——与
  其他风格化场景是同样的事件，只是呈现方式不同。
- `dotnet run --project examples/<名称> -- --classic`——单独运行示例。

**翻译后的追踪可通过语言选择器获得。** `--lang es|zh-CN` 会通过示例提交的术语表
(`glossary.json`)重新渲染同一次运行：标识符会被翻译，取值保持字节级一致，未翻译的
短语会出现在"术语缺口"页脚中。在未使用 `--classic` 的交互式终端中，只要示例的术语表
包含一种以上的语言，`demo.sh` 就会提示你选择语言；选择器只列出术语表实际包含的语言，
候选集合为 `es` 和 `zh-CN`。

启动器兼容 bash 3.2(原装 macOS 的 shell 就能运行)且需要 `awk`；在 Windows 上，
Git Bash 和 WSL 无需改动即可运行。`demo.ps1` 是一个轻量的 PowerShell 封装——静默构建、
运行、打印——没有着色的逐步回放；它是在没有 Windows 机器的情况下编写的，刻意保持精简。

## 示例详解

### ecommerce——生产风格的服务调用图

最完整的示例。`ECommerceDemo` 运行六个场景：

1. **成功下单 + 异步通知**——正常路径，其中返回 `Task` 的通知在线程池线程上完成并
   汇入同一条追踪；渲染为缩进文本、叙述文本和 Mermaid 时序图。
2. **支付失败——库存泄漏 bug**——追踪暴露出 `IInventoryService.Reserve` 被调用了，
   而 `Release` 从未被调用：这是追踪揭示真实 bug 的演示。
3. **不稳定的外部服务**——一个装饰器(`FlakyNotificationService`)包装模拟的网关，
   第一次成功，随后失败；用 `NarrativeTraceProxy.Create` 手工接线，没有容器。
4. **未知客户**——输入校验失败分支。
5. **缺货**——业务规则失败分支，另外还渲染为 PlantUML 时序图标记。
6. **显式异步捕获**——`AsyncLocal` 上下文流入 `Task.Run`，然后 `ForkJoinGroup` 与
   `FireAndForgetGroup` 给并发工作分配隔离的子上下文，并在汇合时合并回父上下文
   (`ConcurrencyScenario`)。

关键辅助类：`ECommerceExample`(`BuildContainer`——`ServiceCollection` 加上
`AddNarrativeTracing`；`BuildTracedOrderService`——同一调用图的手工接线版)、
`OrderService`(产生有趣追踪的编排逻辑)，以及目录、库存、支付、客户和通知的简单内存
适配器，让追踪保持易读。

### clarity——清晰度分析器奖励什么、惩罚什么

酒店预订领域上的四个场景，每个处于不同的命名质量档位：

1. **客人预订房间**——优秀的领域专属命名(`DefaultReservationService`)。
2. **通过 manager 预订**——尚可但表达力较弱的命名(`DefaultBookingManager`)。
3. **遗留数据处理**——刻意薄弱的命名(`DefaultDataProcessor`)，分析器应当扣分。
4. **客人仓储操作**——一个聚焦内聚性的场景。

运行完所有场景后，它把捕获的追踪交给 `ClarityAnalyzer`，并打印 `ClarityReportRenderer`
的输出，这样你就能把每个分数与导致它的命名选择对应起来。

### minecraft——命名质量的直接对比

两个部分完成相当的"玩家进入世界"工作：

- `Refactored.cs`——领域丰富的名字：`IWorldGenerator`、`IPlayerInventory`、
  `ICraftingTable`、`ICreatureSpawner`、`IWorldServer`。
- `Unrefactored.cs`——同样的意图藏在泛化标签后面：`IDataProcessor`、`IStateManager`、
  `IThingFactory`、`IEntityHandler`、`IGameManager`。

`MinecraftExample` 把两者背靠背运行，便于并排比较追踪，并以 `ClarityScanner` 给两半打出的
分数收尾。它是关于命名与可观测性的教学辅助，不是玩法示例。

### library——F# 使用方

一个小型图书借阅领域(`ICatalogService`、`IMemberService`、`ILendingService`)，
从 F# 通过 `NarrativeTraceProxy` 追踪，包含一次成功借阅和一个 `BookUnavailableException`
失败场景，渲染为文本、叙述文本和 Mermaid。F# 接口使用与 C# 相同的特性
(`[<Narrated>]`、`[<OnError>]`、`[<NotTraced>]`)，记录通过 `[<NarrativeSummary>]` 成员
渲染。不需要任何编译器开关：.NET 在元数据中保留参数名，所以追踪读到的就是写下的 F# 名字。

### common——共享的演示工具

`DemoRun` 拥有共享的 `SyncNarrativeContext`(其 `DualPathPipeline` 上挂着实时流)，
为每个场景打开一个 `traceId` 日志作用域，并打印段落标记；`ConsoleLoggerFactory` 是各次
运行用来写日志、无依赖的 `ILoggerFactory`，支持精简或经典格式；`DemoOptions` 解析
`--classic`。它是示例脚手架，不是产品代码——真实应用会把自己的日志提供程序接到同一个
`ILogger` 接缝上。

## 质量门禁

示例不参与打包，但**并不**豁免代码质量：Roslyn 与 Sonar 分析器、20 NCSS 的方法长度门禁、
`dotnet format` 和测试套件全都适用(`./build.sh Verify`)。F# 项目会被 `dotnet format`
和 C# 分析器跳过，因为它们不覆盖 F#。
