# 隐私与脱敏

[English](../privacy-and-redaction.md) | [Español](../es/privacidad-y-ocultacion.md) | [Português](../pt-BR/privacidade-e-ocultacao.md) | **简体中文**

NarrativeTrace 运行在你的进程内部，写出你的团队会共享的文件 — CI 产物、
本地追踪输出，或者你的日志管道会转发的任何东西。这一页准确说明了什么会
被脱敏、什么不会，都是对照这个实现的代码验证过的(不是假设的，也不是从别的
实现照搬过来的)，这样你在接入之前就能判断它对你的数据是否安全。

## 脱敏，逐个接入方式

这个实现里每一种发布出去的集成方式都通过同一个引擎(`ValueRenderer`、
`NarrativeInterceptor`)渲染参数和返回值。其中大多数解析到
`RedactionPolicy.Default`，没有办法改变这一点；`NarrativeTraceProxy`
这条路径是唯一能接受不同策略的接入方式 *(since 0.1.4, unreleased)*：

| 接入方式 | 能接入自定义 `RedactionPolicy` 吗? | 为什么 |
|---|---|---|
| `NarrativeTraceProxy.Create<T>` / `.Create`(原生 `DispatchProxy` 捕获) | **能**，通过 `new ProxyOptions(Redaction: ...)` *(since 0.1.4, unreleased)* | 把这个策略接入这个拦截器发起的每一次 `ValueRenderer.Render` 调用(参数、嵌套对象遍历、返回值)，也接入顶层参数名的判定 — 参见[配置指南 §6](../guides/zh-CN/配置指南.md#6-脱敏)。显式给出时，它会*替换*默认判定而不是扩大它，所以在这里设置 `RedactionPolicy.Disabled` 真的会端到端关闭基于名称的脱敏。`0.1.3`(当前 nuget.org 发布版)完全没有 `ProxyOptions.Redaction`。 |
| DI 自动包装(`AddNarrativeTracing`) | 不能 | 内部用 `NarrativeTraceProxy.Create` 包装，但没有传入 `ProxyOptions`；`NarrativeTracingDiOptions` 目前还没有任何脱敏字段。 |
| ASP.NET Core 中间件 | 不能 | `NarrativeTraceOptions` 没有任何脱敏字段；追踪来自不管哪条 proxy 路径产出的结果。 |
| xUnit 的 `NarrativeFixture` | 不能 | 这个类型里任何地方都没有 `RedactionPolicy`/`RenderOptions` 参数。 |
| NUnit 的 `NarrativeTestBase` | 不能 | 与 xUnit fixture 形状相同。 |
| `[Narrated]` / `[OnError]` 模板占位符(`NarrationResolver`) | 不能 | 完全静态的类，硬编码为 `RedactionPolicy.Default` — 参见下面更窄的那个缺口。 |
| 规范 JSON / 结构化 JSON 投影 | 不适用 — 没什么可关的 | 消费的是已经渲染过(已经脱敏过)的字符串；结构化投影还会无条件地剔除每一个值。 |
| 结构化 `.nt` 产物 | 不适用 — 不存在值 | `StructuralTraceRenderer` 只输出名称、层级和结果类型，从不输出值。 |
| `dotnet-narrativetrace clarity-scan` | 不适用 — 从不读取值 | 仅基于 `MetadataLoadContext` 的反射：它从不构造实例，也不调用任何东西，所以根本没有值需要脱敏。 |
| 在**你自己的代码**里自定义调用 `ValueRenderer.Render(value, options)` | 能 | 自己传入 `new RenderOptions(Redaction: ...)`。即便如此，`[NotTraced]` 仍然会脱敏。 |
| 以上所有接入方式，以累加的方式 | 能，但只能*扩大* | `NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS`(逗号分隔的字段名模式)在进程启动时就并入了 `RedactionPolicy.Default` 本身，所以它也能触达这张表里所有还写着"不能"的接入方式 — 包括那些完全没有按调用配置钩子的。它只能新增模式，不能移除或替换，而且由于读入的是一个 `static readonly` 字段，必须在进程里任何代码第一次碰到 `RedactionPolicy` 之前就设置好。 |

DI 和 ASP.NET Core 这两行是仍然敞开的缺口：给
`NarrativeTracingDiOptions`/`NarrativeTraceOptions` 加上同样的
`Redaction` 字段，并把它接入它们内部构造 `ProxyOptions` 的地方，是一项
已提出但尚未实现的后续工作。

## 拒绝列表能捕捉什么，什么规则优先于它

`RedactionPolicy.Default` 匹配 26 个不区分大小写的名称模式，而不是你随手
翻一眼 FAQ 就能猜到的那个更短的 "password、cvv、ssn、token、secret、
authorization" 集合：

```
password, passwd, secret, token, apikey, api_key, cvv, ssn, authorization,
credential, privatekey, private_key, cardnumber, card_number, jwt, cookie,
setcookie, set_cookie, sessionid, session_id, accountnumber, account_number,
routingnumber, routing_number, pan, iban
```

匹配是基于子串的，而且刻意偏向过度脱敏(`token` 这个模式也会捕捉到
`apiTokenValue`) — 除了 `pan` 和 `iban`，如果按子串匹配，它们会连带
遮蔽掉普通的业务字段(`companyName`、`planId`、`spanCount`、
`japaneseAddress`)，所以这两个改成按标识符的词法边界匹配。

与字段名无关，第二条轴线识别三种**值形态**，不管字段叫什么名字都会脱敏：
一个 JWT(三段 base64url，首段以 `eyJ` 开头)、一个通过 Luhn 校验的
13–19 位支付卡号，以及一个 HTTP `Set-Cookie` 形态的字符串。这就是为什么
一个叫 `data` 或 `note` 的字段，只要碰巧装着看起来像卡号或 bearer token
的东西，照样会被脱敏。

`[NotTraced]` 加在参数、属性或字段上时总是优先于拒绝列表，与它无关：

- 加在属性/字段上时，值的 getter **完全不会被调用** — 脱敏检查在反射
  触及这个成员之前就已经运行，而不是之后。
- 加在 proxy 参数上时，参数已经被调用方求过值了(对一次真实的方法调用来说
  这是不可避免的)，但 NarrativeTrace 本身从不渲染它 — 标记在
  `ValueRenderer` 看到它之前就已经被替换掉了。
- 它优先于*容器*成员上一个精心编写的 `ToString()` 和一个
  `[NarrativeSummary]` 方法：脱敏检查在到达两者之前就已经完成。
- 字典的**键**走的是与值相同的受保护路径 — 一个名字敏感的键，脱敏方式
  与一个名字敏感的属性完全一样，永远不会通过裸的 `ToString()` 渲染。

那个更窄、已经知道的缺口：模板占位符解析(`[Narrated]`/`[OnError]`)是一条
完全静态的代码路径，始终使用 `RedactionPolicy.Default`，**即便这个 proxy
是带着自定义的 `ProxyOptions.Redaction` 创建的也一样**。一个
`[Narrated("issued {token}")]` 模板会用默认拒绝列表来替换 `token`，不管
同一个 proxy 用什么策略渲染它捕获的参数和返回值 — 这是接入
`NarrativeTraceProxy` 的自定义策略唯一触达不到的地方。

## 边界与转义

不管是否脱敏，每一个渲染出来的值都有上限，并且会被净化：

| 控制项 | 默认值 |
|---|---|
| 最大字符串长度 | 200 个字符，之后接一个 `"...(truncated)"` 风格的后缀 |
| 最大集合项数 | 5，之后接一个 `(N total)` 摘要 |
| 最大对象键数 | 5 |
| 最大嵌套深度 | 4 |
| 循环检测 | 基于引用同一性，与深度无关 |
| 控制字符 / 日志注入转义 | 控制字符和不成对的代理项会被转义成 `\uXXXX`(引号/反斜杠是序列化器的职责，不是渲染器的) |

## 保证

- **脱敏在每一种发布出去的集成方式里默认都是无条件的**，而且除非应用
  代码在自己的源码里刻意让某个 proxy 退出，否则一直保持这样：`[NotTraced]`
  和 26 个模式的拒绝列表(加上三种值形态)适用于这个实现发布的每一条输出
  路径 — proxy 捕获、DI 自动包装、ASP.NET Core 中间件、xUnit/NUnit 测试
  输出、模板占位符，以及每一种导出格式 — 除非那个具体的 proxy 是用
  `new ProxyOptions(Redaction: ...)` 构造出来的。没有任何开关、环境变量
  或 MSBuild 属性能关闭脱敏；只有这一个显式的、可评审的构造参数才能做到，
  而且即便如此 `[NotTraced]` 仍然会脱敏。
- **结构化产物完全不携带任何运行时值。** `.nt` 文本产物和可选开启的
  `.structural.json` 条目数组都会剔除每一个参数值、返回值和异常消息 —
  一个属性测试会向一条已捕获条目的每一个值字段注入恶意内容，只要有任何
  一点存活到了投影结果里，测试就会失败。
- **一旦一个类型带有公开状态，它自己的 `ToString()` 就永远不会被信任。**
  一个 record 或一个类，只要暴露出至少一个公开属性或字段，就总是通过反射
  遍历这些成员、走同一条经过脱敏检查的路径来渲染 — 一个在拒绝列表里或标了
  `[NotTraced]` 的成员，在任何代码读到它的值*之前*就已经被替换成了标记，
  而这个类型自己的 `ToString()` 从来不会被调用来产生输出，在任何嵌套深度
  都是如此。一个手写的 `ToString()`，哪怕直接拼接了一个拒绝列表里的字段
  (`return "Account[password=" + password + "]";`)，也无法绕过这一点：
  反射会转而渲染这个对象，那段手写的文本从来不会被走到。反射之外唯一的
  入口是你自己命名的 `[NarrativeSummary]` 成员 — 见下面的非保证。一个完全
  没有公开成员的类型(没有东西可以遍历)是唯一会用到它自己 `ToString()`
  的情形，即便如此，结果也会像任何其他字符串一样被清洗并限长。
- **渲染不能让你的应用崩溃。** 捕获和渲染在触及调用方代码的三个点上都是
  异常隔离的：一个会抛异常的自定义 `ToString()`、一个会抛异常的
  `[NarrativeSummary]` 成员，以及一个在反射内省中(包括被模板点名)被
  访问时会抛异常的属性/字段 getter。每一种都会把*那一部分*退化为一个带
  类型的 `<error: TypeName>` 占位符 *(since 0.1.4, unreleased)*
  — 只携带被捕获异常自身的类型名，例如
  `<error: InvalidOperationException>`，绝不携带它的 `.Message`(消息里
  可能带着渲染本想保护的那个值本身)— 而不会中止这次调用、这个集合或这条
  追踪。一个会抛异常的 `[NarrativeSummary]` 也是同样退化，而不会退回去
  渲染那个类型的字段：摘要之所以被精心编写，正是为了不把字段原样展示出来。
  这是一道 `try`/`catch` 防线，不是一道栈深度防线 — 一个递归的 `ToString()`
  抛出的 `StackOverflowException` 是 CLR 层面的、任何托管处理程序都无法
  捕获的故障，所以它根本走不到这条路径上来。真正挡住一个递归类型的，是
  反射遍历自身的 `MaxDepth` 上限和基于引用同一性的循环防线 — 这也是为什么
  一个类型自己的 `ToString()` 只会在一个没有公开成员可遍历的叶子值上被
  调用，而绝不会在正在递归的那个复合对象上被调用。一个恶意的枚举器或
  字典是另一类风险，同样受到保护，但不在这三个被点名的入口之列，它会
  退化为一个不带类型的 `<error>`，而不是带类型的形式。
- **资源使用是有界的。** 长度、集合大小、对象宽度和嵌套深度全部都有上限，
  加上与深度无关的、基于引用同一性的循环检测。
- **输出无法被伪造。** 控制字符和不成对的代理项，在一个渲染出来的值到达
  文件之前就已经被转义，所以一个恶意的值无法注入一条伪造的日志行，也无法
  破坏 Markdown/JSON/图表的语法。
- **测试产物落在一个临时位置，而不是版本控制里。** xUnit 和 NUnit 的测试
  集成默认会把文件写到测试项目下的 `TestResults/narrativetrace/` ——
  `dotnet test`/Visual Studio/Rider 本就把这里当作可丢弃输出，本仓库自身
  的 `.gitignore` 也已经排除了它。设置 `NARRATIVETRACE_OUTPUT=false`
  可以彻底关闭写入，或者用 `NARRATIVETRACE_OUTPUT_DIR` 重定向；里面有
  什么、是否应该进入你自己的仓库，见[应提交的内容](应提交的内容.md)。

## 非保证

- **DI 自动包装和 ASP.NET Core 中间件还没有暴露脱敏钩子。**
  `NarrativeTraceProxy.Create`/`.Create<T>` 接受 `new ProxyOptions(Redaction: ...)`，
  但 `AddNarrativeTracing` 和 `AddNarrativeTrace` 构造它们的 proxy 时不带
  这个参数 — 在你自己的源码里刻意去做(把 `ProxyOptions` 传给一次直接的
  `Create` 调用，或者用进程级别的环境变量
  `NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS`)仍然是在这两条路径上
  扩大或替换脱敏的唯一方式。即便在 `RedactionPolicy.Disabled` 之下，
  `[NotTraced]` 仍然会脱敏。
- **模板占位符不遵循自定义的 `RedactionPolicy`。**
  `[Narrated]`/`[OnError]` 的解析始终使用默认拒绝列表，哪怕这个 proxy 是
  带着自定义的 `ProxyOptions.Redaction` 创建的。
- **检测是基于名称和形态的，不是统计意义上的。** 没有信息熵之类的、"看起来
  随机"的启发式判断 — 一个躺在名字无害、形态不被识别的字段里的机密不会被
  捕捉到。这是一道后备防线，不是"每一个机密都会被找到"的保证。
- **一个 `[NarrativeSummary]` 成员一旦被你点名，就是被信任的代码。** 这是
  上面那条保证唯一刻意的例外：给一个成员打上注解，会让那个类型完全跳出
  反射遍历，渲染器只会展示摘要返回的内容 — 与一个普通的 `ToString()`
  不同(对于带公开状态的类型，它永远不被信任)，一个 `[NarrativeSummary]`
  成员*确实*被信任，正是因为点名它本身就是你在自己源码里做出的刻意行为。
  如果摘要本身把某个字段原样带了回来，那是你写的摘要自己选择暴露它，与
  你在调试器里读到的手写 `ToString()` 是同一种信任模型 — 而不是渲染器
  引入的漏洞。如果它抛异常，值就会退化为带类型的 `<error: TypeName>`
  占位符 *(since 0.1.4, unreleased)*，而绝不会泄露它原本会展示的内容。如果一个类型自己的摘要不能被
  信任放进某个字段，就改为在那个*成员*上标注 `[NotTraced]`。
- **目前还没有任何生产环境的基线比较循环会把结构化产物读回来。** `.nt`
  文件按构造是确定性的、不含值的，但这个实现 没有发布任何东西会把它与
  上一次运行做比较(参见[应提交的内容](应提交的内容.md))。
