# 选择集成方式

[English](../choosing-an-integration.md) | [Español](../es/elegir-una-integracion.md) | [Português](../pt-BR/escolhendo-uma-integracao.md) | **简体中文**

NarrativeTrace 提供了好几种让一次调用被追踪的方式。这一页是帮你做决定的，
不是教程 — 每条路径背后的代码，参见[安装指南](../guides/zh-CN/安装指南.md)。

## 你想要... / 从这里开始...

| 你想要 | 从这里开始 |
|---|---|
| 在测试里追踪，仪式感最少 | xUnit 的 `NarrativeFixture` 或 NUnit 的 `NarrativeTestBase` |
| 明确控制到底包装了什么，纯 .NET 方式 | `NarrativeTraceProxy.Create<T>`(一个 `DispatchProxy`) |
| 某个命名空间下每一个注册到 MS.DI 的接口服务都自动被追踪 | `AddNarrativeTracing`(.NET 版的 Spring/Micronaut Bean 追踪等价物) |
| 生产环境中 ASP.NET Core 的 HTTP 请求生命周期 | `NarrativeTrace.AspNetCore` 中间件 |
| 针对编译好的程序集、无需运行测试的 CI 命名质量门禁 | `dotnet-narrativetrace clarity-scan` + `clarity-check`，或 `NarrativeTrace.MSBuild` 包 |
| 把追踪接入你现有的 `ILogger` 管道 | `NarrativeTrace.Logging`(`AddNarrativeLogging()`) |
| OpenTelemetry Span，批量或实时 | `NarrativeTrace.Observability` |
| 追踪旁边的时序图(Mermaid/PlantUML) | `NarrativeTrace.Diagrams` |
| 完全零代码改动 — 一个你不掌控其接线方式的应用 | **尚未发布。** 已规划(免费) — CLR 上还没有决定 Java `-javaagent` 的等价方案；源生成器与 IL weaving 之间选哪个，是尚待解决的问题。参见[功能指南](../feature-guide.md)。 |

## 怎么决定

这个实现 中的每条路径都挂接在**接口边界**上 — 今天没有字节码织入，也没有
零代码选项(上面那一行)。真正的问题是*如何*到达那个接口调用：

```
你在写测试吗？
  是 -> xUnit？ -> NarrativeFixture
        NUnit？ -> NarrativeTestBase(从它派生)

  否 -> 被包装的实例是你自己构造/持有的吗？
           是 -> 它是按接口注册在 MS.DI 里的吗？
                    是 -> AddNarrativeTracing(按命名空间匹配的自动包装)
                    否 -> 直接用 NarrativeTraceProxy.Create<T>
           否 -> 这是一个 ASP.NET Core 的 HTTP 请求边界吗？
                    是 -> NarrativeTrace.AspNetCore 中间件
                    否 -> 零代码接入还是已规划状态，尚未发布 — 在假设
                          它存在之前，先看看功能指南
```

在此之上，与上面的答案无关：

- 也想让追踪进入你现有的日志流？在你选定的捕获路径旁边加上
  `NarrativeTrace.Logging`。
- 想要 OpenTelemetry Span？加上 `NarrativeTrace.Observability` — 它从一棵
  已完成的 `TraceTree`(批量)或一个实时事件流导出，所以它是叠加在上面任意
  一条路径之上，而不是取代它。
- 想要把命名质量门禁作为构建的一部分，与是否运行测试无关？
  `NarrativeTrace.MSBuild`/CLI 通过反射从一个**编译好的程序集**出发工作，
  而不是从已捕获的追踪出发 — 与这一页其他一切都不同的数据来源。

## 每条路径共有的一点

不管你包装的是什么，只有**接口**调用是可见的 — `DispatchProxy` 从构造上
就只作用于接口，所以实现内部的私有和内部调用永远不会被单独追踪。如果你
想要更细粒度的叙事，就把你关心的行为拆到它自己的接口后面。脱敏、边界和
异常隔离在每条路径上都是一致的 — 参见[隐私与脱敏](隐私与脱敏.md)；没有
哪种集成方式"更可信"到可以放宽这些约束。

## 每条路径的注意事项

- **`NarrativeTraceProxy.Create<T>`** — `T` 必须是接口，目标必须实现它；
  不匹配时会看到底层 .NET 反射异常(`DispatchProxy.Create`/
  `MethodInfo.Invoke`)，而不是 NarrativeTrace 专属的异常。参见
  [故障排查](故障排查.md)。
- **`AddNarrativeTracing`** — 一定要**最后**调用，在它应该看到的每个服务
  都已经注册之后；包装只会触及调用那一刻已经存在的描述符。命名空间匹配
  是按点分边界的(`MyApp.Services` 永远不会匹配 `MyApp.ServicesExtra`)，
  对于按工厂注册的服务，匹配的是**接口**的命名空间，因为在注册时刻实现
  类型是不透明的。键控服务和开放泛型会被静默地保留为未包装状态。
- **ASP.NET Core 中间件** — 把 `UseMiddleware<NarrativeTraceMiddleware>()`
  放在管道靠外侧的位置。在中间件运行之前调用
  `HttpContext.GetNarrativeContext()` 的代码(或者是一条被排除的路径)，
  会得到一个静默的空操作上下文，而不是异常 — 请求会正常完成，只是没有
  被追踪。
- **xUnit 的 `NarrativeFixture`** — 一个 fixture 持有一个上下文，因此一次
  只服务一个测试；`IClassFixture<NarrativeFixture>` 是安全的，因为 xUnit
  不会在一个类内部并行，但如果把同一个实例共享给会并行运行的多个类，它们
  的 span 会合并进同一条追踪。
- **NUnit 的 `NarrativeTestBase`** — 从它派生；setup/teardown 的接线是
  自动的，`OnTraceComplete` 是你写文件或运行清晰度分析的重写点。
- **`clarity-scan`** — 需要一个真实的、已编译的 .NET 程序集路径；它从不
  执行程序集，只反射其元数据。

## 平台上限

- `net10.0` — 完整能力，包括 `NarrativeTrace.AspNetCore`(目前仅
  `net10.0`)。
- `netstandard2.0` — 除 ASP.NET Core 中间件外的一切。
- `net48` — 通过 `NarrativeTrace.Legacy`；在任何平台上都能编译，但
  Windows 上的运行时验证仍待完成(参见[功能指南](../feature-guide.md))。
