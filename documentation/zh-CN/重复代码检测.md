# 重复代码检测

[English](../duplication.md) | [Español](../es/deteccion-de-duplicacion.md) | [Português](../pt-BR/deteccao-de-duplicacao.md) | **简体中文**

*(自 0.1.5 起，尚未发布)* —— 这是构建期工具，不是运行时库的行为：这里的内容
不会随 NuGet 包一起发布。

`./build.sh DuplicationReport` 运行 [jscpd](https://github.com/kucherenko/jscpd)
（固定的精确版本，通过 `npx jscpd@<版本>` 调用 —— 本仓库自身的类路径上并没
有像 Java 运行时的 CPD 那样现成的 JVM/PMD 等价物），扫描主源码和测试源码中
的 C# 文件，并在每次提交时写出一份报告。`./build.sh DuplicationCheck` 读取
该报告并执行下文所述的重复率棘轮机制；它是 `Verify` 的一部分。

## 度量对象

- **语言：目前仅限 C#**（下文是每个运行时共用的家族级模式）。
- **词元下限：60。** 低于 60 个词元的匹配通常只是巧合——两个互不相关的方法
  碰巧共享一段简短、常见的形状——而不是值得处理的结构性复制。
- **忽略标识符和字面量。** jscpd 的 `--ignore-identifiers
  --ignore-literals` 标志会找出*结构性*重复（形状相同、名称和取值不同），
  而不仅仅是名称相同的粘贴文本——已用一对仅在标识符名称和字面量取值上不同
  的测试文件验证过：在相同词元下限下，不加这两个标志时找到 0 个克隆，加上
  之后找到 1 个克隆（占该对文件行数的 46%）。`--mode strict` 是完全不同的
  另一个维度（它*关闭*了 jscpd 的注释/空白规范化），本身并不会忽略标识符
  或字面量。
- **主源码树和测试源码树分开扫描。** 测试树（`tests/**` + `benchmarks/**`）
  会被报告——其数字会出现在 `duplication.json` 和摘要行中——但从不会使
  `DuplicationCheck` 失败。测试脚手架代码天然会重复（准备逻辑、fixture 构造
  器、断言块）；在那里设一个固定阈值只会带来噪音，而不是信号。

## 棘轮机制，而非固定百分比

单一的"高于 N% 就失败"数字是错误的度量方式：正确的数字取决于词元下限，以及
源码树中有多少内容天然重复（数据表、生成代码），因此固定阈值要么松到永远
不会触发，要么紧到会阻塞无关的工作。`DuplicationCheck` 转而针对一份已提交
的基线 `config/duplication/baseline.properties` 执行棘轮机制：

- **当主源码树的百分比比记录的基线高出超过 0.3 个百分点时失败**——这一小
  段容差用于吸收多次运行之间词元计数的噪音，而不是真正的增长。
- **当某个非豁免的簇比基线中记录的最大簇还要大时失败**——即使整体百分比保
  持不变，单独出现一个新的大型重复块本身也是一个发现。
- **无论测试树的百分比是多少，都不会使该检查失败。**

在移除某处重复的同一次提交中降低基线。绝不要为了让失败消失而调高基线——
应改为添加一条有理由的豁免（见下文），或者把这个发现留到以后再处理。

## 豁免即数据

`config/duplication/exemptions.txt` 列出了刻意保留的重复：这些代码是故意
构造成两份平行副本，而不是共享的抽象。每一条记录是一对 `globA :: globB`
（与 jscpd 报告的、相对于仓库根目录的路径匹配，通过 `Microsoft.Extensions.
FileSystemGlobbing` 完成——该库已经通过 Nuke.Common 存在于本构建的依赖图
中），其正上方是一行 `# 理由`。只有当一个簇的*每一处*出现都匹配该对模式中
的一个时，它才算被豁免——这是一条默认拒绝的规则，因此任何未分类、超过下限
的簇始终是一个发现，绝不会被悄悄放过。没有理由行的豁免对，或格式不正确的
豁免对，会直接导致构建失败，而不是被忽略。

首次扫描记录下来的唯一一条豁免，曾经是 clarity 模块的词表字典
（`src/NarrativeTrace.Clarity/*Dictionary.cs`）。2026-09-12 的一项所有者
裁定（与 Java 运行时自身的豁免分类保持一致）将其扩展为三个有理由的类
别，各自写成独立的 `globA :: globB` 行，而不是合并成一行（这个 glob 引擎
不支持花括号的多选写法）：**按文件名识别的词表**——`TraceNamer.cs` 的
形容词/名词/动词词表，针对自身以及针对 clarity 字典；**按内容形状而非文
件名识别的词表**——`GenericTokenDetector.cs` 和 `RedactionPolicy.cs` 的
`HashSet`/数组字面量词表，即便这两个文件都不匹配 `*Dictionary` 这个
glob，它们彼此之间以及与字典之间仍会聚簇；以及**宽记录**——
`CanonicalEntry.cs` 和 `SpanContext.cs`，二者都是单个位置记录，每个 schema
字段对应一个可空分量（这是本运行时对 Java 运行时"每个分量一个 setter"的
构建器类的对应写法），针对自身以及彼此互相豁免，因为把按字段分量的写法
折叠起来会改变公共构造函数的接口。这些豁免对中的每一对都记录了任何已知
的缺口——同一个 glob 也（必然地）覆盖了与其豁免的数据挨在一起的真实逻
辑，而不是悄悄扩大"数据而非逻辑"这句话的含义。

## 阅读报告

`artifacts/duplication/duplication.json` 是规范化后的结果（这是每个
NarrativeTrace 运行时的重复检测工具都会输出的统一格式，无论它覆盖哪些语
言）：

```json
{"tool":"jscpd","language":"csharp","minTokens":60,
 "main":{"tokensTotal":N,"tokensDuplicated":N,"percent":x.y,
         "clusters":[{"tokens":N,"lines":N,
                       "occurrences":[{"file":"…","startLine":N,"endLine":N}]}]},
 "test":{"...":"same shape"}}
```

`tokensDuplicated` 是一个**并集**，而不是对所有簇求和——按"词元数 × 出现
次数"计数会把多个簇共同覆盖的区域重复计算两次、三次（Java 运行时首次扫描
在修正为并集之前测出超过 300% 的重复率，正是这一类错误），因此 `percent`
永远不会超过 100%。jscpd 是按文件各自分词的，而不是像 PMD 的 CPD 那样把整
个语料合并成一条共享的词元流，而且它的 JSON 报告完全没有携带按出现位置区
分的词元索引——每处出现只有起止行号，再加上整段匹配片段的一个词元计数——
因此本运行时的并集计算改为在每个文件各自的行号区间上进行：先按文件对出
现位置分组，把同一文件内相互重叠或相邻的区间合并，每个合并后的区间只计
一次，取构成它的各个区间中*最大*的词元数，而不是把它们相加。只要一个文件
内的重复区间彼此相同或互不重叠——包括"同一段落、多个匹配对象"这种朴素求
和会算错的常见情形——这个计算就是精确的；只有在同一文件内两个不同的簇发
生真正罕见的重叠时，它才是保守估计。完整推理见
`DuplicationReportSupport.UnionDuplicatedTokens`。

构建日志每次运行会打印一行摘要：

```
duplication: main 12.8% of tokens in 137 clusters (largest 1558 tokens
src/NarrativeTrace.Core/TraceNamer.cs:29 ↔ src/NarrativeTrace.Core/TraceNamer.cs:65)
· test 26.7% in 912 clusters (reported, not gated)
```

## 缺少 Node/npx 绝不会被悄悄放过

jscpd 是一个外部的 Node 命令行工具，而不是本构建自身依赖图中已有的库——所
以，与 Java 运行时的 PMD-CPD（一个始终存在的库依赖）不同，
`DuplicationReport`/`DuplicationCheck` 有可能遇到完全没有 Node 的环境。这
遵循与 `SecretsScan`/`Semgrep`/`OsvScan` 相同的 `ScannerGateSupport` 约定：
在本地，缺少 `npx` 会**发出警告**，并在
`artifacts/duplication/scan-status/` 下记录一个 `skipped` 状态——绝不是悄
悄地显示为通过；在 CI 中，或在任何要求必须具备重复检测工具的场景下，缺失
会**导致构建失败**。当 `DuplicationReport` 没有产出 `duplication.json`
时，`DuplicationCheck` 本身也会大声地失败（而不是"没有基线，那就算通
过"）——这正是发布回顾第 2 条规则：一个优雅跳过的工具，必须能证明自己确
实曾经运行过。

各环境的 Node 可用性：

| 环境 | 是否有 Node？ |
|---|---|
| 本地开发容器 | **有**——Node 22（该容器中本就已预置） |
| GitHub Actions CI（`ci.yml`，`ubuntu-latest`） | **有**——运行器镜像中已预装 |
| 私有 CI（`mcr.microsoft.com/dotnet/sdk` 镜像） | **默认没有**——`verify` 任务的 `before_script` 会通过 NodeSource 安装 Node 22，与开发容器保持一致 |
| 发布前验证容器（发布脚本，同一个精简 SDK 镜像，非 root） | **默认没有**——会在宿主机上下载一份固定版本的 Node 压缩包，并以只读方式挂载进容器（非 root 容器运行无需 root/apt） |

## 添加一条豁免

1. 运行 `./build.sh DuplicationReport`，在 `duplication.json` 或摘要行中
   找到对应的簇。
2. 确认这是刻意为之——是特意保持分离的真正平行结构，而不是没人来得及清理
   的重复代码。
3. 在 `config/duplication/exemptions.txt` 中添加一行 `# 理由` 和一对
   `globA :: globB`。
4. 重新运行 `./build.sh DuplicationCheck`，确认检查通过。

## 降低基线

先移除重复代码，运行 `./build.sh DuplicationReport`，然后在同一次提交中把
`config/duplication/baseline.properties` 里的 `main.percent` /
`main.largestCluster` 更新为新测得的数字——这与本构建已经用于覆盖率和变异
得分下限的"以实测值为准"的做法完全一致。
