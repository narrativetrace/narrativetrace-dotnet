# 故障排查

[English](../troubleshooting.md) | [Español](../es/solucion-de-problemas.md) | [Português](../pt-BR/solucao-de-problemas.md) | **简体中文**

症状 → 原因 → 修复，全部取自这个实现 自己的代码和测试。如果某个问题是
已知但尚未覆盖的粗糙边缘，而不是已经证实的保证，这一页会明确标出来 —
它说的是今天真正成立的事，而不是说起来好听的承诺。

## 一个参数被渲染成 `arg0`、`arg1`，而不是它的真实名称

**原因：** 捕获代码读取的是 `ParameterInfo.Name`，只有在编译后的元数据从未
携带参数名时它才是 `null` — 动态构建的委托(`System.Reflection.Emit`)，或
某些由 interop 生成的接口。**由 `dotnet build` 编译的普通 C#/F# 代码总是
保留参数名**，包括 Release 构建和裁剪(trimming)之下，所以正常使用中不应
该出现这种情况。

**修复：** 如果你遇到了，检查一下这个接口是不是来自某个代码生成器，或者
某条丢弃了参数元数据的动态程序集路径。这是与 JVM 唯一的差异：普通代码在
.NET 里完全不需要任何 `-parameters` 编译器开关。

## `NarrativeTraceProxy.Create<T>` 在启动时抛出异常

**原因：** `T` 不是接口，或者目标没有实现它。这个实现 在这里没有添加任何
自己的守卫子句 — 你看到的异常是底层的 .NET 反射异常
(`DispatchProxy.Create`)，不是 NarrativeTrace 专属的异常。

**修复：** 确认 `T` 是一个接口类型，并且你要包装的实例确实实现了它。

## 一个 DI 注册的服务没有被追踪

**原因**，以下任意一种：

- 它不是按**接口**注册的 — `AddNarrativeTracing` 只包装按接口类型的
  注册。
- 它的实现命名空间不匹配任何已配置的前缀。匹配是按点分边界的：
  `MyApp.Services` 永远不会匹配 `MyApp.ServicesExtra`。
- 它是一个**键控服务**，或者是一个**开放泛型** — 两者都会被静默地保留为
  未包装状态。
- `AddNarrativeTracing` 是在服务注册**之前**调用的 — 包装只会触及调用那
  一刻已经存在的描述符。
- 它是按工厂注册的，匹配退化到了**接口**的命名空间(因为在注册时刻实现
  类型是不透明的) — 这可能与真实实现的命名空间不同。

**修复：** 最后调用 `AddNarrativeTracing`，仔细核对命名空间前缀，对需要
追踪的服务避免使用键控/开放泛型注册。

## ASP.NET Core 请求没有显示追踪，也没有报错

**原因：** 只要中间件没有存放任何东西，`HttpContext.GetNarrativeContext()`
就会返回一个静默的空操作上下文 — 一条被排除的路径，或者是在管道中
`UseMiddleware<NarrativeTraceMiddleware>()` 之前运行的代码。请求会正常
完成；只是没有被追踪。

**修复：** 把中间件放在管道靠外侧的位置，如果某条具体路由悄无声息，就检查
一下 `ExcludedPaths`。

## 后台 `Task.Run` 的工作丢失了，或者显示为一个单独的根节点

**原因：** 对于在一个 `RunAsync` 作用域内**启动并被观察到**的工作，
`AsyncLocal` 上下文能正确流转。一个裸的 `Task.Run`，如果在它所在的作用域
关闭时仍在运行，会在**执行时刻而不是提交时刻**附着 — 这是一个已记录的
分歧，不是 bug — 所以它可能作为第二个根节点出现，而不是嵌套在启动它的
那次调用之下。

**修复：** 使用 `AsyncNarrativeContext.RunAsync`、`ForkJoinGroup` 或
`FireAndForgetGroup` 来获得你真正需要的血缘保证，而不是一个裸的
`Task.Run`。

## `CaptureTrace()` 返回一棵空的追踪树，而你期望有内容

**原因：** 从任何 `AsyncNarrativeContext` 作用域之外读取捕获结果 — 或者
在两个作用域并发运行之后读取 — 会刻意返回一棵**空**树，而不是别人的树。
一段缺席的叙事是诚实的；别人那次请求的叙事就不诚实了。

**修复：** 从产生这份工作的那个作用域内部捕获，或者确保在捕获之前已经
`await` 了这份工作。

## 一次 fire-and-forget 的失败永远不会出现在任何地方

**原因：** `FireAndForgetGroup` 按设计吞掉已启动工作中的异常 — 这正是
"即发即弃"之所以安全的原因 — 并把失败的分支排除在 `ChildRoots` 之外。这是
有意的隔离，不是缺失的功能。

**修复：** 如果你需要观察这个失败，在启动的工作内部加上你自己的处理；不要
依赖追踪来暴露它。

## `ForkJoinGroup` 的分支跑完了，但它们的 span 却不见了

**原因：** 跳过 `await fork.JoinAsync()` 意味着这些分支的 span 永远到不了
父级追踪 — 工作本身照常执行，只是叙事把它弄丢了。

**修复：** 一定要 `await` 这个 join。

## 两个 xUnit 测试的追踪混在了一起

**原因：** 一个 `NarrativeFixture` 持有一个上下文，因此一次只服务一个
测试。`IClassFixture<NarrativeFixture>` 是安全的，因为 xUnit 从不在一个
类内部并行 — 但如果把一个 fixture 实例共享给会并行运行的多个类(或者通过
一个集合)，它们的 span 会合并进同一条追踪。

**修复：** 让每个测试类拥有自己的 fixture 实例；不要在并行的测试集合之间
共享一个。

## `clarity-scan --assembly` 崩溃，而不是打印一条干净的错误

**原因：** 一个缺失的文件会被干净地处理(`error: assembly not found`，
退出码 `1`)。一个**存在但无效**的文件 — 不是真正的 .NET 程序集 — 就不是
这样了：它是通过 `MetadataLoadContext` 加载的，没有任何守卫，所以一个
格式错误的文件会以一个原始的、未处理的 .NET 异常出现，而不是文档记录过的
退出码之一。这是一个已知但尚未覆盖的粗糙边缘，不是文档记录过的行为。

**修复：** 仔细核对这条路径是否真的指向一个已编译的 .NET 程序集。如果你
遇到了这个崩溃，值得把它报告出来，而不是绕开它。

## 一个 `NARRATIVETRACE_*` 的拼写错误悄无声息地什么都不做

**原因：** 按设计，每一个 `NARRATIVETRACE_*` 环境变量在遇到无法识别的值时
都会退化为它的默认值，而不是抛出异常 — "错误的配置永远不应该让捕获崩溃"。
`NARRATIVETRACE_LEVEL=Detial`(拼写错误)会悄悄地解析为 `Detail`，而不是
报错。

**修复：** 不要指望拼写错误会被发现 — 仔细核对拼写，或者在启动时把解析
出来的配置记录下来，以便确认。

## 输出默认就是开启的，却没有任何追踪文件出现

**原因**，以下任意一种：

- 上游某处设置了 `NARRATIVETRACE_OUTPUT=false`(一个 CI 变量、
  `.runsettings` 里的环境覆盖、父级 shell)—— 这是唯一一个能关闭这个
  默认开启的写入器的开关 *(since 0.1.4, unreleased)*。
- `NARRATIVETRACE_LEVEL` 是 `Off` — 从未捕获过任何东西。
- 这棵追踪树确实是空的。**按设计，一棵空的追踪树什么都不写** — 一个
  缺失的产物意味着"没有捕获到任何东西"，而不是"写入失败了"。这通常意味着
  测试调用的是裸的、未包装的服务，而不是经过 proxy 包装的那个。
- 你找错地方了：如果没有设置 `NARRATIVETRACE_OUTPUT_DIR` 覆盖，文件会落在
  相对于测试运行工作目录的 `TestResults/narrativetrace/` 下，而不是仓库
  根目录。

**修复：** 确认 `NARRATIVETRACE_OUTPUT` 没有被设为 `false`，确认级别不是
`Off`，确认你是通过 `NarrativeTraceProxy.Create<T>`(或者一个自动包装的
DI 服务)调用的，而不是裸实现，并检查测试项目下的
`TestResults/narrativetrace/`。

## `clarity-report.md` 和我从 `NARRATIVETRACE_OUTPUT` 预期的对不上

**原因：** 套件级别的 `clarity-results.json`/`clarity-report.md` 只要套件
fixture 运行过并且累积了至少一条条目就会被写出 — **与
`NARRATIVETRACE_OUTPUT` 无关**。只有按测试的 `.md`/`.json`/`.mmd`/`.nt`
文件才受那个开关控制(默认开启；`false` 可以关闭)。

**修复：** 不要把"没有按测试的追踪文件"当成"没有清晰度报告" — 它们受两个
不同条件的控制。

## 术语表采集从来不写任何东西

**原因：** 采集是否开启，取决于**文件是否存在**这一条件 —
`GlossarySuiteReporter` 除非在它解析出的位置(向上目录查找、
`NARRATIVETRACE_GLOSSARY`，或者字面量 `off`)已经存在 `glossary.json`，
否则会静默地什么都不做。

**修复：** 如果你想让采集运行起来，就自己提交一份初始的 `glossary.json` —
参见
[应提交的内容](应提交的内容.md#术语表采集是否开启取决于文件是否存在)。

## 引用 `NarrativeTrace.MSBuild` 把它拉进了我这个包的依赖里

**原因：** 它本来就应该是一个仅构建期的依赖。

**修复：** 用 `PrivateAssets="all"` 引用它，这样它就不会传递流向你自己那个
NuGet 包的消费者。
