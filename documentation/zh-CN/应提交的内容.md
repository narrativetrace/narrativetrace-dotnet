# 应提交的内容

[English](../what-to-commit.md) | [Español](../es/que-incluir-en-el-commit.md) | [Português](../pt-BR/o-que-incluir-no-commit.md) | **简体中文**

一旦追踪运行起来，磁盘上就会有生成出来的文件。这一页说明哪些是可以随时
丢弃的输出，哪些是应该被评审并提交的 — 都是对照这个实现 的 writer
实际产出的内容验证过的，不是凭空假设的。

## 逐一说明每个产物

| 产物 | 提交吗? | 为什么 |
|---|---|---|
| `<output-dir>/traces/<Class>/<slug>.md` | 不 | 每次运行都会重新生成；一个测试的、人类可读的追踪。 |
| `<output-dir>/traces/<Class>/<slug>.json` | 不 | 同一条追踪的 JSON 章节文档 — 每次运行都会重新生成。 |
| `<output-dir>/diagrams/<Class>/<slug>.mmd` | 不 | 配套的 Mermaid 时序图 — 每次运行都会重新生成。 |
| `<output-dir>/structural/<Class>/<slug>.nt` | 目前不 | 不含值的结构化追踪(只有名称、层级、结果类型)。按构造是确定性的、可 diff 的，但**这个实现 里目前没有任何东西会把它读回来** — 没有审批模式，也没有针对上一次运行的增量比较循环，所以也就没有可以拿来比较的、已提交的基线。和其他文件一样，每次运行都会重新生成。 |
| `<output-dir>/traces/<Class>/<slug>.canonical.json` | 不 | 可选开启(`NARRATIVETRACE_CANONICAL_JSON=true`)的一致性 fixture，是用来针对规范 schema 测试 NarrativeTrace 自身的 — 不是应用项目需要保留的东西。 |
| `<output-dir>/traces/<Class>/<slug>.structural.json` | 不 | 可选开启(`NARRATIVETRACE_STRUCTURAL_JSON=true`)的、不含值的条目数组 — 与 `.canonical.json` 同样的道理。 |
| `<output-dir>/clarity-results.json` | 不 | 生成出来的套件级清晰度报告(机器可读)。只要套件 fixture 运行过并且累积了至少一条条目就会出现，与 `NARRATIVETRACE_OUTPUT` 无关 — 重新生成，不要提交。 |
| `<output-dir>/clarity-report.md` | 不 | 同一份报告，人类可读版本。 |
| `clarity/clarity-scan-results.json` / `clarity-scan-report.md`(来自 `dotnet-narrativetrace clarity-scan`) | 不 | 对一个编译好的程序集做的静态、仅反射扫描 — 在 CI 里重新生成，不要提交。 |
| `glossary.json` | **要**，如果你使用术语表采集 | 见下文 — 这是这个实现 里唯一一个被当作已评审、手工维护的文件的产物。 |
| `glossary.md` | **要**，与 `glossary.json` 一起 | 同一个文件的人类可读渲染，只有当 JSON 的字节发生变化时才会重写(防抖动)。 |
| `<output-dir>/glossary-usage.json` | 不 | 每次运行的易失性使用统计 — 会重新生成，不需要维护。 |

`<output-dir>` 在没有设置 `NARRATIVETRACE_OUTPUT_DIR` 时默认是
`./narrativetrace-output`。把它加进 `.gitignore`，除非你有具体的 CI 理由
要把它归档为构建产物(这是一个 CI 保留策略的决定，不是"提交到版本控制"的
决定)。

## 术语表采集是否开启取决于文件是否存在

与这一页上其他一切不同，术语表采集不会凭空创建任何东西：除非
`glossary.json` **已经存在**于它解析出的位置(从测试运行处向上查找目录、
`NARRATIVETRACE_GLOSSARY` 环境变量，或者用字面量 `off` 彻底关闭这个功能)，
否则 `GlossarySuiteReporter` 会静默地什么都不做。如果你想要采集，就自己
提交一份初始文件：

```json
{
  "schemaVersion": 1,
  "contexts": {},
  "terms": []
}
```

从那以后，套件的每次运行都会从它的追踪中采集新的词汇，把它增量式地合并进
`glossary.json`，并重新生成 `glossary.md` — 像评审任何其他手工维护的文件
一样评审这个 diff。一个格式错误的 `glossary.json` 会抛出异常，而不是被静默
跳过，这是有意为之的：一个已提交、已评审的文件里的拼写错误应该大声地
失败。

## 这个实现目前还没有的东西

审批模式目前还没有：这个实现
没有 `.approved.nt` / `.received.nt` 文件，没有 `approve` 这个动词，也没有
任何东西会把一次运行的结构化追踪与上一次的做比较。`.nt` 结构化产物是
存在的，而且是确定性的，但这一页上的每一个产物今天都只是重新生成型的
输出 — 还没有一个"已提交的基线，一旦出现未经评审的行为变化就让构建失败"
的工作流可以接入。
