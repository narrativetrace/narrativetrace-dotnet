# 应提交的内容

[English](../what-to-commit.md) | [Español](../es/que-incluir-en-el-commit.md) | [Português](../pt-BR/o-que-incluir-no-commit.md) | **简体中文**

一旦追踪运行起来，磁盘上就会有生成出来的文件。这一页说明哪些是可以随时
丢弃的输出，哪些是应该被评审并提交的 — 都是对照这个实现 的 writer
实际产出的内容验证过的，不是凭空假设的。

## 逐一说明每个产物

| 产物 | 提交吗? | 为什么 |
|---|---|---|
| `<output-dir>/traces/<Class>/<slug>.md` | 不 | 每次运行都会重新生成；一个测试的、人类可读的追踪。 |
| `<output-dir>/traces/<Class>/<slug>.json` | 不 | 同一条追踪的 JSON 章节文档 — 每次运行都会重新生成。 |
| `<output-dir>/diagrams/<Class>/<slug>.mmd` | 不 | 配套的 Mermaid 时序图 — 每次运行都会重新生成。 |
| `<output-dir>/manifest.json` | 不 | 每次运行都会重新生成；它顶层的 `run` 对象(`id`、`name` —— 这次运行自己的三词短语)命名的是*这一次运行*而不是某个场景，所以即使其他一切都没变，它每次运行也会变 *(since 0.1.4, unreleased)*。 |
| `<output-dir>/structural/<Class>/<slug>.nt` | 不 | 不含值的结构化追踪(只有名称、层级、结果类型)。磁盘上的这个文件就是**最近一次通过(last green)的基线** *(since 0.1.4, unreleased)*：一次通过的运行会让它前进，一次没通过的运行会与它比较(套件汇总里的 "Since last green" 那一行、失败报告里的增量)，但绝不会覆盖它。它仍然不是需要提交的东西 — 已提交的对应物见[结构化追踪格式](../structural-trace-format.md)。 |
| `<approved-dir>/<Class>/<slug>.approved.nt` | **要**，如果[审批模式](../structural-trace-format.md)已开启 | *(since 0.1.4, unreleased)* 经过评审的已批准追踪 — `NARRATIVETRACE_APPROVED_DIR`(默认 `narratives`)，用 `NARRATIVETRACE_APPROVAL=true` 开启。这是这张表里唯一一个属于深思熟虑的决定、而不是输出的文件。 |
| `<approved-dir>/<Class>/<slug>.received.nt` | 不 | 在审批不一致时写出，或者在还没有已批准追踪时写出。评审它，运行 `./build.sh Approve` 来提升它(或者手动重命名)，然后让提升操作把它删掉 — 绝不要提交收到的追踪本身。 |
| `<output-dir>/traces/<Class>/<slug>.canonical.json` | 不 | 可选开启(`NARRATIVETRACE_CANONICAL_JSON=true`)的一致性 fixture，是用来针对规范 schema 测试 NarrativeTrace 自身的 — 不是应用项目需要保留的东西。 |
| `<output-dir>/traces/<Class>/<slug>.structural.json` | 不 | 可选开启(`NARRATIVETRACE_STRUCTURAL_JSON=true`)的、不含值的条目数组 — 与 `.canonical.json` 同样的道理。 |
| `<output-dir>/clarity-results.json` | 不 | 生成出来的套件级清晰度报告(机器可读)。只要套件 fixture 运行过并且累积了至少一条条目就会出现，与 `NARRATIVETRACE_OUTPUT` 无关 — 重新生成，不要提交。 |
| `<output-dir>/clarity-report.md` | 不 | 同一份报告，人类可读版本。 |
| `clarity/clarity-scan-results.json` / `clarity-scan-report.md`(来自 `dotnet-narrativetrace clarity-scan`) | 不 | 对一个编译好的程序集做的静态、仅反射扫描 — 在 CI 里重新生成，不要提交。 |
| `glossary.json` | **要**，如果你使用术语表采集 | 见下文 — 这是这个实现 里唯一一个被当作已评审、手工维护的文件的产物。 |
| `glossary.md` | **要**，与 `glossary.json` 一起 | 同一个文件的人类可读渲染，只有当 JSON 的字节发生变化时才会重写(防抖动)。 |
| `<output-dir>/glossary-usage.json` | 不 | 每次运行的易失性使用统计 — 会重新生成，不需要维护。 |
| `.claude/skills/<segment>/SKILL.md` | **要** | 由 `dotnet run --project src/NarrativeTrace.Cli -- skills render` 从类型化的技能目录重新生成，但仍需提交：它必须发布在 Claude Code 能发现的确切路径上。若它与最新渲染结果出现偏差，`skills lint` 会让构建失败。 |
| `AGENTS.md` 中 `<!-- narrativetrace:skills:start -->` … `<!-- narrativetrace:skills:end -->` 之间的部分 | **要** | 由同一个渲染器就地拼接进文件——请提交整个文件，而不仅仅是这一部分。 |

追踪写入**默认开启** *(since 0.1.4, unreleased)*(设置 `NARRATIVETRACE_OUTPUT=false` 可以关闭)；
`<output-dir>` 在没有设置 `NARRATIVETRACE_OUTPUT_DIR` 时默认是
`./TestResults/narrativetrace` —— 这是 `dotnet test --results-directory`
以及 Visual Studio/Rider 本就当作可丢弃输出的 `.NET` 约定，也是本仓库自身
`.gitignore` 已经排除的目录。在你自己的项目里也应该让它远离版本控制，
除非你有具体的 CI 理由要把它归档为构建产物(这是一个 CI 保留策略的决定，
不是"提交到版本控制"的决定)。

## 术语表采集是否开启取决于文件是否存在

与这一页上其他一切不同，术语表采集不会凭空创建任何东西：除非
`glossary.json` **已经存在**于它解析出的位置(从测试运行处向上查找目录、
`NARRATIVETRACE_GLOSSARY` 环境变量，或者用字面量 `off` 彻底关闭这个功能)，
否则 `GlossarySuiteReporter` 会静默地什么都不做。如果你想要采集，就自己
提交一份初始文件：

```json
{
  "schemaVersion": 1,
  "contexts": {},
  "terms": []
}
```

从那以后，套件的每次运行都会从它的追踪中采集新的词汇，把它增量式地合并进
`glossary.json`，并重新生成 `glossary.md` — 像评审任何其他手工维护的文件
一样评审这个 diff。一个格式错误的 `glossary.json` 会抛出异常，而不是被静默
跳过，这是有意为之的：一个已提交、已评审的文件里的拼写错误应该大声地
失败。

## 审批模式，从头到尾

```text
测试通过
   |
   v
把当前结构与已批准的追踪比较
   |
   +-- 相同    --> 通过，什么都不写
   +-- 不同    --> 写出 .received.nt 并让测试失败
                     |
                     v
                有人评审这份 diff
                     |
                     v
                ./build.sh Approve
                     |
                     v
              .approved.nt 已更新，提交它
```

失败状态是刻意设计的：一个通过了的测试，如果它的*结构*发生了变化 ——
包括 AI agent 在一次原本正确的重构里悄悄带进来的变化 —— 就必须被人看到
并明确批准，而不能只是编译通过就算数。审批模式的完整行为见
[结构化追踪格式](../structural-trace-format.md)，`NARRATIVETRACE_APPROVAL`
/ `NARRATIVETRACE_APPROVED_DIR` 见[配置指南](../guides/zh-CN/配置指南.md)。
