## 实用方案

每个问题一页，用用户会输入的话来写，每页都附带一次真实运行的代码和输出。

- [给这个服务加日志](../../zh-CN/实用方案/给这个服务加日志.md) — 不写一条日志语句，就把每次调用（含参数名和结果）送进项目自己的 `ILogger`。
- [帮我调试并修复这个缺陷](../../zh-CN/实用方案/帮我调试并修复这个缺陷.md) — 找出流程中缺失的调用、修复它，并把修复后的流程固定为已批准的基线。
- [这个测试为什么失败了](../../zh-CN/实用方案/这个测试为什么失败了.md) — 对照断言读一个红色测试的叙述，分清是代码缺陷还是过时的预期。
- [修改复杂流程前先审查它](../../zh-CN/实用方案/修改复杂流程前先审查它.md) — 在 `Detail` 和 `Summary` 两个级别看流程做了什么，以及智能体读取的无值 `.nt`。
- [审查重构：行为变了吗](../../zh-CN/实用方案/审查重构行为变了吗.md) — 借助批准差异，抓住绿色测试没发现的被删调用。
- [跨服务追踪一次请求（分布式追踪）](../../zh-CN/实用方案/跨服务追踪一次请求.md) — 让同一个追踪 id 和调用方的 span 跨过一次 HTTP 调用，使两个服务的日志读起来像同一个请求。
- [别让密钥进日志](../../zh-CN/实用方案/别让密钥进日志.md) — 看密码和卡号如何按名称和按值被遮蔽，并用一个回读日志的测试来证明。
- [跨线程追踪一个流程](../../zh-CN/实用方案/跨线程追踪一个流程.md) — 用 fork-join 组让后台工作留在追踪之内，并看看没有它时是什么样子。
- [把追踪发到你已有的可观测性栈](../../zh-CN/实用方案/把追踪发到你已有的可观测性栈.md) — 把同一次运行同时交给你的日志器和 OpenTelemetry span，并排查看。
- [在生产环境追踪而不付出代价](../../zh-CN/实用方案/在生产环境追踪而不付出代价.md) — 用 `Errors` 级别只保留失败的运行，并了解它丢掉了什么。

## 理念

**代码即日志。** 方法名、参数名和返回值本身就讲述了运行时的故事。
NarrativeTrace 自动捕获这个故事，并把它渲染成可读的叙事 — 于是你写的是
干净、富有表达力的代码，而不是手写的日志语句，只在例外情况下才使用特性。
