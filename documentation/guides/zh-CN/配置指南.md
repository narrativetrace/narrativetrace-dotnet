# NarrativeTrace .NET — 配置指南

[English](../configuration.md) | [Español](../es/guia-de-configuracion.md) | [Português](../pt-BR/guia-de-configuracao.md) | **简体中文**

本指南说明 NarrativeTrace 的运行时配置与构建期配置。

## 配置面

| 方式 | 机制 | 适用场景 |
|---|---|---|
| 编程式 | `NarrativeTraceConfig` 构造函数 | 任何应用 — 直接控制 |
| 环境变量 | `NARRATIVETRACE_*` 变量(`ConfigResolver`) | CI、容器、测试宿主 |
| 依赖注入 | `AddNarrativeTracing(options => …)` | 使用 MS.DI 的应用 |
| ASP.NET Core | `AddNarrativeTrace(configuration)` + `"NarrativeTrace"` 配置节 | Web 应用 |
| MSBuild | `NarrativeTrace*` / `Clarity*` MSBuild 属性 | 构建期清晰度门禁 |

## 1. 追踪级别(`NarrativeTraceConfig`)

上下文由 `NarrativeTraceConfig` 创建，其默认级别为 `Detail`。

```csharp
using NarrativeTrace.Core;
using NarrativeTrace.Runtime;

var config = new NarrativeTraceConfig(TracingLevel.Narrative);
var context = new SyncNarrativeContext(config);
```

可用级别(枚举 `TracingLevel`，由低到高)：

| 级别 | 行为 |
|---|---|
| `Off` | 不捕获任何追踪。 |
| `Errors` | 只捕获异常路径。 |
| `Summary` | 根入口、最深的叶节点，以及完整的异常链。 |
| `Narrative` | 完整调用流程，但不记录参数值。 |
| `Detail` | 完整调用流程，并带参数值与返回值。 |

级别在运行时可变(`config.Level = TracingLevel.Errors;`)。`IsActive()` 在
`Errors` 及以上为 `true`(只有 `Off` 会停用捕获)；`CapturesParameterValues`
仅在 `Detail` 下为 `true`。

### 服务身份

为每个 Span 标记稳定的进程身份，以便跨服务关联：

```csharp
var identity = new ServiceIdentity(
    ServiceName: "order-service",
    ServiceVersion: "2.0.0",
    Environment: "production");

var config = new NarrativeTraceConfig(TracingLevel.Detail, identity);
```

它们会在 JSON 导出、日志作用域和 OpenTelemetry Span 中呈现为
`service.name` / `service.version` / `service.environment`。

### Traceparent 播种 *(since 0.1.4, unreleased)*

播种一个初始的 [W3C `traceparent`](https://www.w3.org/TR/trace-context/#traceparent-header)，
让每个由该配置构建出的上下文都延续调用方的追踪，而不是另起一条——这是
`NarrativeTraceMiddleware` 从入站请求中采纳的做法（见下面的第 4 节）的
无 HTTP 请求头版本：

```csharp
var config = new NarrativeTraceConfig(
    initialTraceparent: Traceparent.Parse("00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"));
var context = new SyncNarrativeContext(config);
```

`Traceparent.Parse` 永远不会抛出异常——一个格式错误或缺失的值会返回
`null`，`NarrativeTraceConfig` 会把它当作"没有种子"处理，于是由它构建出
的上下文会回退到一条全新的、随机生成的追踪。它和 `ServiceIdentity` 一样
在构造时就固定下来：没有 setter，要给一个正在运行的上下文重新播种，需要
直接调用 `context.AdoptTraceparent(...)`。

生产流量请不要设置它——由同一个共享 `NarrativeTraceConfig` 构建出的每个
上下文都会采纳同一个固定值，这对单个顶层上下文（一个演示、一个一次性
脚本）来说是对的，但会破坏 `AsyncNarrativeContext` 让每个作用域拥有各自
独立追踪的全部意义。不要把这两者搭配使用。

## 2. 环境变量(`ConfigResolver`)

`ConfigResolver` 读取六个变量 — 这是 `.NET` 原生的覆盖通道，让 `Core`
保持零依赖。无效取值会**退化为默认值而不是抛出异常**，因此错误的配置绝不
会让捕获崩溃。

| 变量 | 取值 | 默认值 |
|---|---|---|
| `NARRATIVETRACE_LEVEL` | `Off`、`Errors`、`Summary`、`Narrative`、`Detail` | `Detail` |
| `NARRATIVETRACE_OUTPUT` | `true` / `false`(或 `1` / `0`) | `true` |
| `NARRATIVETRACE_OUTPUT_DIR` | 任意可写路径 | `TestResults/narrativetrace` |
| `NARRATIVETRACE_FORMAT` | `Markdown`、`Text`、`Prose`、`Json` | `Markdown` |
| `NARRATIVETRACE_CANONICAL_JSON` | `true` / `false`(或 `1`) | `false` |
| `NARRATIVETRACE_STRUCTURAL_JSON` | `true` / `false`(或 `1`) | `false` |
| `NARRATIVETRACE_APPROVAL` | `true` / `false`(或 `1`) | `false` |
| `NARRATIVETRACE_APPROVED_DIR` | 任意可写路径 | `narratives` |

级别与格式的解析是宽容的(不区分大小写与标点：`detail`、`DETAIL` 和
`Detail` 都能解析)。

`NARRATIVETRACE_OUTPUT` **默认开启**(负责人裁决，2026-09-11)
*(since 0.1.4, unreleased)*：xUnit
fixture 和 NUnit 基类写出的按测试产物，正是采用这个库的回报，所以写入
不需要任何开关就会发生。只有显式设置 `NARRATIVETRACE_OUTPUT=false`(或
`0`)才会关闭它；`true`/`1` 会被当作无操作接受，方便仍然显式设置它的
脚本。如果没有 `NARRATIVETRACE_OUTPUT_DIR` 覆盖，文件会落在
`TestResults/narrativetrace/` 下 —— 这是 `dotnet test
--results-directory` 以及 Visual Studio/Rider 本就当作可丢弃的 `.NET`
约定，也是本仓库自身 `.gitignore` 已经排除的目录。

```csharp
var resolved = ConfigResolver.Resolve();          // 读取进程环境变量
var config = new NarrativeTraceConfig(resolved.Level);
```

`Resolve()` 返回
`ResolvedConfig(Level, Output, OutputDir, Format, CanonicalJson, StructuralJson)`。

后两个开关控制写在追踪文件旁边的机器可读产物，与主格式无关：

- `<test>.canonical.json` — 把追踪压平成规范 schema 条目(每次调用一个
  `method_enter` 和一个 `method_exit`)，供 schema 消费方与跨平台一致性
  fixture 使用。
- `<test>.structural.json` — 同一个数组，但省略了所有运行时值(ADR-002
  第 1 级)，用于交给 AI 消费方：参数名会保留，而参数值、返回值和异常消息
  不会。

两者默认都是关闭的：它们是机器产物，而不是给人读在追踪旁边的东西。

`NARRATIVETRACE_APPROVAL` 用来开启审批模式 *(since 0.1.4, unreleased)*：
一个测试**通过**之后，场景不含值的结构(与 `.nt` 产物同样的渲染)会与
已提交的已批准追踪
`<approvedDir>/<TestClassSimpleName>/<artifact_name>.approved.nt` 做比较
—— 与其他每一个按测试产物一样的产物身份，所以一个运行多次的方法会有
一个按调用的已批准追踪。如果还没有已批准追踪，或者结构不一致，测试就
会带着可读的 diff 失败，并把当前结构写在旁边，命名为 `*.received.nt`；
评审它，然后通过 `Approve` 构建目标(`./build.sh Approve`)接受它，或者
手动重命名。一个失败测试的结构永远不会被验证 —— 它还处于半途，不应该
去搅动已收到的追踪。`NARRATIVETRACE_APPROVED_DIR` 指定这些基线所在的
目录(默认 `narratives`)。完整行为见
[结构化追踪格式](../../structural-trace-format.md)，哪些文件该提交见
[应提交的内容](../../zh-CN/应提交的内容.md)。

## 3. 依赖注入

`AddNarrativeTracing` 会包装那些以接口注册、且实现类命名空间匹配已配置
前缀的服务(Spring/Micronaut Bean 自动包装在 `.NET` 中的等价物)。

```csharp
using NarrativeTrace.DependencyInjection;

services.AddNarrativeTracing(options =>
{
    options.Level = TracingLevel.Detail;           // 默认：Detail
    options.Namespaces("MyApp.Orders", "MyApp.Payments");
});
```

行为：

- 只考虑**接口**类型的服务；开放泛型会被跳过(`DispatchProxy` 的限制)。
- 命名空间匹配使用**点边界**语义：`MyApp.Orders` 匹配 `MyApp.Orders` 和
  `MyApp.Orders.Sub`，但不匹配 `MyApp.OrdersLegacy`。
- 原注册的**生命周期会被保留**(Singleton 仍是 Singleton，等等)。
- 会自动注册一个 **Scoped** 的 `INarrativeContext`；同一作用域内所有被
  包装的服务共享它，因此它们的调用会嵌套成一棵树。
- 对于按工厂或按实例注册的服务，使用其具体实现类的命名空间；若无法获得，
  则回退使用服务类型(接口)的命名空间。

## 4. ASP.NET Core

`AddNarrativeTrace` 会绑定名为 `NarrativeTrace` 的可选 `IConfiguration`
配置节，然后允许一个委托对其进行覆盖。

```csharp
builder.Services.AddNarrativeTrace(builder.Configuration, options =>
{
    options.Level = TracingLevel.Detail;
    options.ExcludedPaths.Add("/health");
    options.ExcludedPaths.Add("/metrics");
});
```

`appsettings.json`：

```json
{
  "NarrativeTrace": {
    "Level": "Detail",
    "ExcludedPaths": [ "/health", "/metrics" ]
  }
}
```

| 键 | 类型 | 用途 |
|---|---|---|
| `Level` | `TracingLevel` | 请求上下文的捕获级别。 |
| `ExcludedPaths` | `string[]` | 被完全跳过的路径前缀(按段匹配)。 |

`NarrativeTraceMiddleware` 会自动采纳入站的 `traceparent` 请求头
*(since 0.1.4, unreleased)*——没有开关可以关闭它；缺失、格式错误或版本
被禁止的请求头会被忽略，请求会得到一条全新生成的追踪，其原理与上面按
配置播种的方式相同，只是驱动它的是调用方的请求头，而不是一个固定值。

中间件与导出器的接线详见
[ASP.NET Core 集成指南](ASP.NET-Core集成指南.md)。

## 5. MSBuild

`NarrativeTrace.MSBuild` 包是 `dotnet-narrativetrace` CLI 之上的一层薄
封装 — 所有阈值逻辑都在 CLI 中。它声明了以下可覆盖的属性：

| 属性 | 默认值 | 用途 |
|---|---|---|
| `NarrativeTraceOutput` | `false` | 向测试宿主传递 `NARRATIVETRACE_OUTPUT=true`。 |
| `NarrativeTraceOutputDir` | `$(MSBuildProjectDirectory)/narrativetrace` | 结果与追踪的写入位置。 |
| `NarrativeTraceFormat` | `markdown` | 追踪输出格式。 |
| `NarrativeTraceLevel` | `DETAIL` | 测试宿主的捕获级别。 |
| `ClarityMinScore` | `0.0` | 总体评分低于此值时让构建失败。 |
| `ClarityMaxHighIssues` | `2147483647` | HIGH 问题数超过此值时让构建失败。 |
| `ClarityWarnOnly` | `false` | 把门禁失败降级为警告。 |

它还注册了两个目标：

- **`ClarityScan`**(依赖 `Build`) — 对构建产物程序集做仅反射扫描，输出
  到 `clarity-results.json`。
- **`ClarityCheck`**(依赖 `ClarityScan`) — 运行门禁；通过 `.stamp` 文件
  实现增量，因此当 `clarity-results.json` 未变化时会跳过重复检查。

```bash
# 把阈值作为构建的一部分强制执行：
dotnet build /t:ClarityCheck /p:ClarityMinScore=0.80 /p:ClarityMaxHighIssues=0
```

必须先安装该工具(`dotnet tool install --global NarrativeTrace.Cli`，或使用
本地工具清单)。

## 6. 脱敏

反射式的值渲染是**默认脱敏，而非默认泄露**。当被追踪的对象没有精心编写的
摘要时，`ValueRenderer` 会反射其属性 — 但基于名称的拒绝列表
(`RedactionPolicy.Default`)会在渲染前，把字段名匹配敏感模式(`password`、
`secret`、`token`、`apikey`、`cvv`、`ssn`、`authorization`、`credential`、
`privatekey`、`cardNumber`、`jwt`、`cookie`、`setCookie`、`sessionId`、
`accountNumber`、`routingNumber`、`pan`、`iban`……)的值替换为 `[REDACTED]`。

```csharp
var options = new RenderOptions(
    MaxStringLength: 200,
    MaxArrayItems: 5,
    MaxObjectKeys: 5,
    MaxDepth: 4,
    Redaction: RedactionPolicy.OfPatterns(["ssn", "pan"]));  // 自定义拒绝列表
```

- `RedactionPolicy.Default` — 内置的拒绝列表。
- `RedactionPolicy.OfPatterns(...)` — 你自己的、不区分大小写的子串模式。
- `RedactionPolicy.Disabled` — 关闭脱敏(值原样渲染，同时也关闭下文的按值
  形态脱敏)。

除 **`pan` 和 `iban`** 外，其余模式均按子串匹配 — 这两个模式改为按标识符
的词法边界匹配：若按子串匹配，`pan` 会连带遮蔽 `companyName`、`planId`、
`spanCount` 等普通业务字段，`iban` 同理。`cardPan`、`ibanNumber` 仍会匹配
(模式在名称中构成完整的词)，但 `companyName` 不会。

**按值形态脱敏是第二条、与字段名无关的规则。** 无论字段叫什么名字(甚至
没有名字 —— 例如裸返回值、列表中的一项)，只要字符串在结构上符合 JWT
(三段 base64url，首段以 `eyJ` 开头)、通过 Luhn 校验的银行卡号(13–19 位
数字，允许 `[ -]` 分隔符)，或 HTTP `Set-Cookie` 头的取值(`名称=值` 之后
跟着如 `Path=`、`Secure` 等具名属性)，就会被遮蔽。规则刻意保持狭窄 ——
不使用信息熵之类的启发式判断 —— 因此未通过 Luhn 校验的普通数字编号仍会
保持可见。`RedactionPolicy.OfPatterns(...)` 会保留按值形态脱敏(自定义
名称列表并不代表对这些字节形态是否为凭据的判断);只有
`RedactionPolicy.Disabled` 会将其关闭。

对于敏感的**参数**，更推荐使用
[`[NotTraced]`](特性指南.md#nottraced) 特性 — 它按位置脱敏，与名称无关。

**把自定义策略接入 proxy 路径。** 上面的 `RenderOptions` 是你自己调用
`ValueRenderer.Render` 时会用到的东西；要触达*发布出去*的
`NarrativeTraceProxy` 捕获路径，需要另外一步 —— 通过 `ProxyOptions.Redaction`
*(since 0.1.4, unreleased)*：

```csharp
var proxy = NarrativeTraceProxy.Create<IOrderService>(
    new OrderService(), context,
    new ProxyOptions(Redaction: RedactionPolicy.OfPatterns(["ssn", "holderName"])));
```

显式给出时，这个策略会*替换*默认的基于名称的判定 —— 既包括 proxy 参数
自身的名称，也包括嵌套对象反射出来的属性名称 —— 而不是在其基础上扩大，
所以在这里设置 `RedactionPolicy.Disabled` 真的会端到端关闭基于名称的
脱敏(`[NotTraced]` 无论如何都仍然会脱敏)。不设置 `Redaction`(保持
默认)，一个 proxy 的行为就和以前完全一样。

DI 自动包装和 ASP.NET Core 集成暴露了同样的钩子 *(since 0.1.4,
unreleased)*：[`AddNarrativeTracing`](依赖注入指南.md) 上的
`NarrativeTracingDiOptions.Redaction` 会触达这次调用所包装的每一个服务，
[`AddNarrativeTrace`](ASP.NET-Core集成指南.md) 上的
`NarrativeTraceOptions.Redaction` 在两者同时注册到同一个应用时，也同样
会触达自动包装出来的 proxy —— 在任一侧配置的策略，另一侧都能看到，因为
这两个包共享同一个服务集合。`AddNarrativeTracing` 自己的 `Redaction`
一旦设置，会对它包装的服务优先生效。完整的、逐个接入方式的全貌参见
[隐私与脱敏](../../zh-CN/隐私与脱敏.md)。

**不改代码，一次性扩大所有接入方式。**
`NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS`
是一个逗号分隔的字段名模式列表，会并入 `RedactionPolicy.Default` 本身：

```bash
NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS=holderName,betalingskort
```

和 `ProxyOptions.Redaction` 不同，这个只能新增模式，不能移除内置的，
而且能触达上面表格里的每一种接入方式 —— 包括没有任何按调用钩子的 DI
自动包装和 ASP.NET Core 中间件。它只会被读取一次，读进一个
`static readonly` 字段，所以必须在进程里任何代码第一次碰到
`RedactionPolicy` 之前就设置好(应用自己的启动代码，或者一个在运行时
才设置它的测试，都已经太迟了)。

## 7. 日志桥接(`Microsoft.Extensions.Logging`)

用 `NarrativeTrace.Logging` 包把追踪事件接入你现有的日志体系。
`LoggingNarrativeContext` 可以装饰任意上下文，并通过 `ILogger` 记录每次
进入/返回/异常：

```csharp
using NarrativeTrace.Logging;

var inner = new SyncNarrativeContext(new NarrativeTraceConfig());
INarrativeContext context = new LoggingNarrativeContext(inner, logger);
```

若只想把一棵完成的树导出一次，使用 `TraceLogExporter`：

```csharp
TraceLogExporter.ExportToLogger(context.CaptureTrace(), logger);
```

**关于标准控制台 logger 顺序的说明。** 如果上面的 `logger` 是由
`Microsoft.Extensions.Logging.Console` 支持的，它的行默认会通过一个后台
队列写入，所以可能会晚于——或者与——你的进程同步写入的输出
(`Console.Write*`、另一个 provider、捕获 stdout 的测试运行器)交错得很
奇怪 —— 这是控制台 provider 本身的平台行为，不是 NarrativeTrace 的缺陷。
真正管用的修复办法：在任何依赖顺序的代码之前释放(`Dispose`)
`ILoggerFactory`(或控制台 provider)—— 最简单的方式是
`using var loggerFactory = LoggerFactory.Create(...)`；`Dispose()` 会一直
阻塞，直到 provider 的后台写入线程把队列中的一切都写完为止。可参考
60 秒教程["把它发送到你的日志库"](../../zh-CN/60秒.md#把它发送到你的日志库)
一步中已验证过的完整示例。

在带 host 的应用中，请通过 DI 接线**事件流**桥接，而不是自己构造：

```csharp
services.AddNarrativeLogging();   // 和 AddNarrativeTracing 一样，最后调用
```

它会用已注册的 `ILoggerFactory` 构造 `LoggingTraceEventListener` 并注册为
单例，同时把它挂到任何已注册的 `IEventSubscribable` 事件流上，于是解析出来
的事件流就已经在叙事了。有两种情况会让它静默，且都刻意不抛异常：没有注册
`ILoggerFactory`(桥接无处可写)，或 `NARRATIVETRACE_NARRATION=off` 否决了
叙事 —— 这是 Java 的 `narrativetrace.narration=off` 的 .NET 写法。只有
`off` 这一个取值会否决，因此写错时你仍在叙事，而不会被悄悄静音。

结构良好的代码 — 方法短小、命名清晰、计算结果通过返回值而非日志传达 —
本就几乎不需要手写日志调用；NarrativeTrace 会从签名和返回值中捕获故事。
只有对那些不会体现在方法边界上的决策，才穿插 `ILogger` 调用，并在重构时
逐步移除它们。

**一次测试套件运行也有名字** *(自 0.1.4 起,尚未发布)*:只要
`NarrativeTrace.Testing.Xunit` 或 `NarrativeTrace.Testing.NUnit` 有一次
活跃的套件运行,上述两种桥接都会在 scope 中额外加入 `nt.runName` ——
这次运行自己的三词短语,与 `nt.traceId`/`nt.traceName` 并列,这样一次
grep 就能找到某次运行的全部日志行。在被追踪的运行之外则完全不出现。
同一个身份还会命名控制台套件页脚(`run: bold elk soars`)和
`manifest.json` 顶层的 `run` 对象,并出现在 Markdown 追踪文档 frontmatter
的 `run:` 字段以及文本/散文渲染器的起始行前面 —— 但绝不会进入不带值的
结构化 `.nt` 制品(参见
[结构化追踪格式](../../structural-trace-format.md))。

## 8. TracingLevel 与日志级别

这是两个独立的过滤器。**TracingLevel** 控制什么会被*记录*进追踪树(因而
也决定捕获的开销)。**日志级别**控制日志桥接*发出*什么。被 TracingLevel
过滤掉的调用永远不会到达树、渲染器或任何 logger。

| 目标 | 调整方式 |
|---|---|
| 降低日志噪音 | 提高 logger 的级别(树仍会被捕获，供文件/渲染器使用)。 |
| 缩小追踪体积 | 降低 `TracingLevel`(`Narrative` → `Summary`)。 |
| 降低 CPU/内存 | 降低 `TracingLevel` — 日志级别对捕获成本没有影响。 |

## 9. 按环境推荐的默认值

| 环境 | 级别 | 输出 |
|---|---|---|
| 本地功能开发 | `Detail` | 默认开启、`FORMAT=Markdown` |
| CI 测试运行 | `Narrative` 或 `Summary` | 默认开启、`FORMAT=Markdown` |
| 对性能敏感的生产环境 | `Errors`(或 `Off`) | 这里不会运行任何测试 fixture — 不输出文件 |

## 10. 环境变量实例演练

代码读取的每一个 `NARRATIVETRACE_*` 变量都汇总在此处 —— 它设置了什么、
默认值是什么，以及效果的可运行演示。`ConfigResolver` 的变量已在上面的
§2 中介绍；其余变量在各自所属之处介绍(脱敏在 §6，日志桥接在
§7);本节是这些内容的实例演练配套。

| 变量 | 设置内容 | 默认值 |
|---|---|---|
| `NARRATIVETRACE_LEVEL` | 上下文捕获所用的 `TracingLevel`。 | `Detail` |
| `NARRATIVETRACE_OUTPUT` | 是否将每个测试的追踪制品写入磁盘。 | `true` |
| `NARRATIVETRACE_OUTPUT_DIR` | 追踪制品写入的目录。 | `TestResults/narrativetrace` |
| `NARRATIVETRACE_FORMAT` | 主要制品格式(`Markdown`/`Text`/`Prose`/`Json`)。 | `Markdown` |
| `NARRATIVETRACE_CANONICAL_JSON` | 是否额外写入每个测试的规范条目数组。 | `false` |
| `NARRATIVETRACE_STRUCTURAL_JSON` | 是否额外写入每个测试的无值条目数组。 | `false` |
| `NARRATIVETRACE_APPROVAL` | 通过的测试的结构是否与已提交的 `*.approved.nt` 基线进行核对。 | `false` |
| `NARRATIVETRACE_APPROVED_DIR` | 存放批准基线的目录。 | `narratives` |
| `NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS` | 以逗号分隔、并入 `RedactionPolicy.Default` 的额外字段名模式。 | *(无)* |
| `NARRATIVETRACE_NARRATION` | 设为 `off` 时否决日志桥接;其他任何值都保持其开启。 | *(未设置 —— 正在叙述)* |
| `NARRATIVETRACE_GLOSSARY` | 用于套件采集的显式术语表文件路径,或 `off` 以彻底禁用采集。 | 从测试运行处向上查找 `glossary.json` |
| `NARRATIVETRACE_GLOSSARY_PATH` | 用于实时翻译加载的术语表文件,覆盖已部署应用旁边的文件。 | 应用旁边的 `glossary.json`(如果存在) |

### `NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS`

与上面的变量不同,这里在调用点没有代码需要修改 ——
`RedactionPolicy.Default` 自己只读取这个变量一次,存入一个
`static readonly` 字段(上面的 §6)。这意味着演示必须在**自己的进程**
中运行,在变量已经设置好之后才启动,而不是通过其他示例所用的注入式读
取机制 —— 所以这一个是手工核实的,而不是与已提交的源文件进行核对,遵
循支撑本页其余每个示例的同一条规则 8(一次真实的、编译过的运行,而不
是手写的猜测):

```bash
export NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS=holderName,betalingskort
```

```csharp
using NarrativeTrace.Core;

Console.WriteLine(RedactionPolicy.Default.ShouldRedact("holderName"));
Console.WriteLine(RedactionPolicy.Default.ShouldRedact("password"));
```

可观察到的效果 —— 分别在变量未设置、以及变量已设置的情况下各运行一次
(`dotnet run` 两次,是两次独立的进程调用):

```text
# 未设置
False
True

# NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS=holderName,betalingskort
True
True
```

`password` 在两种情况下都会被脱敏(它已经在内置的拒绝列表中);
`holderName` 只有在变量将其加入列表之后才会被脱敏。如果在进程中已经有
代码接触过 `RedactionPolicy` 之后才设置该变量,则不会产生任何效果 ——
参见上面的 §6。

### `NARRATIVETRACE_NARRATION`

```bash
export NARRATIVETRACE_NARRATION=off
```

```csharp
var services = new ServiceCollection();
services.AddSingleton<ILoggerFactory>(NullLoggerFactory.Instance);

services.AddNarrativeLogging(null, key => key == "NARRATIVETRACE_NARRATION" ? "off" : null);

var listener = services.BuildServiceProvider().GetService<LoggingTraceEventListener>();
Console.WriteLine($"listener is null == {listener is null}");
```

可观察到的效果 —— `off`(不区分大小写)会彻底否决注册,即便存在
`ILoggerFactory` 也一样;任何其他值(包括拼写错误)都会让叙述保持开启:

```text
listener is null == True
```
