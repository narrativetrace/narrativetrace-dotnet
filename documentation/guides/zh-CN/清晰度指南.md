# NarrativeTrace .NET — 清晰度指南

[English](../clarity.md) | [Español](../es/guia-de-claridad.md) | [Português](../pt-BR/guia-de-clareza.md) | **简体中文**

如果追踪*就是*代码，那么追踪的质量就是代码的质量。`NarrativeTrace.Clarity`
包会分析你的方法名、类名和参数名，并为它们传达意图的程度评分。

## 两种评分方式

### 基于已捕获的追踪(`ClarityAnalyzer`)

分析一次运行中真正出现过的名称：

```csharp
using NarrativeTrace.Clarity;

var result = ClarityAnalyzer.Analyze(context.CaptureTrace());
Console.WriteLine($"Overall clarity: {result.Overall:F2}");
```

### 基于程序集，无需运行任何代码(`ClarityScanner`)

仅使用反射 — 检查给定类型的公共方法而不执行它们(对 CI 安全)：

```csharp
IReadOnlyDictionary<string, ClarityResult> results =
    ClarityScanner.Scan([typeof(OrderService), typeof(PaymentService)]);

foreach (var (typeName, result) in results)
{
    Console.WriteLine($"{typeName}: {result.Overall:F2}");
}
```

结果以 `Type.Name` 作为键。[`dotnet-narrativetrace` CLI](#构建期强制) 用的
也是它。

## 评分对象

`ClarityResult` 携带一个总体评分，外加五个加权分项(取值均为
`0.0`–`1.0`)：

| 分项 | 权重 | 衡量内容 |
|---|---|---|
| 方法(`Method`) | 30% | 方法名中动词的质量与 token 的专指程度。 |
| 参数(`Parameter`) | 25% | 领域专指程度，相对于泛化或无意义的参数 token。 |
| 类(`Class`) | 20% | 类名的角色后缀质量与前缀专指程度。 |
| 结构(`Structural`) | 15% | 参数个数与调用深度带来的惩罚。 |
| 内聚性(`Cohesion`) | 10% | 方法是否与类的角色后缀相符。 |

```csharp
public sealed record ClarityResult(
    double Overall, double Method, double Class,
    double Parameter, double Structural, double Cohesion,
    IReadOnlyList<ClarityIssue> Issues);
```

### 评分的直觉

- **方法名** — 第一个 token 被视为动词。*领域*动词(`calculate`、
  `validate`、`reserve`)得分最高；*布尔*前缀(`is`、`has`、`can`)得分
  较高；*标准*动词(`create`、`find`)居中；*泛化*动词(`get`、`process`、
  `handle`、`execute`)得分最低。额外的 token 会提升专指程度
  (`reserveInventory` 优于 `reserve`)。
- **类名** — 领域前缀加功能性后缀得分良好(`OrderService`)；只有后缀
  (`Service`)或泛化的 `Manager` 得分很差。
- **参数名** — 领域专属(`customerId`、`checkInDate`)优于按类型泛化
  (`id`、`count`)，后者优于含糊(`data`、`info`)，再优于毫无意义
  (`x`、`tmp`)。
- **结构** — 参数过多或调用链过深的方法会被扣分。
- **内聚性** — 方法会与类的角色后缀所期望的动词做比对(`Repository`
  应当出现 `find`/`save`/`delete`)。

## 问题

`ClarityResult.Issues` 以 `ClarityIssue(Severity, Description, Suggestion)`
的形式列出具体的命名问题。分析器目前把**使用泛化动词的方法名**标记为
`high` 严重级别的问题 — 例如首个 token 是 `get`/`process`/`handle` 的方法：

```
severity:    high
description: Generic verb 'process' in DataProcessor.process
suggestion:  Use a domain-specific verb
```

严重级别是小写的字符串 token(`high`)。`ClarityReportRenderer` 在
Markdown 输出中把严重级别映射为图标。

## 你自己的词汇表,来自你已有的术语表

内置词典懂得通用的软件英语。它们不知道 `Fold` 在你的领域里是一个动词,不知道
`Tranche` 是一个精确的名词,也不知道 `Fx` 是你团队对 *foreign exchange* 认可的
缩写 —— 而它们不认识的名称会被评为未知,而不是领域专属。

你用仓库中已有的词汇文件来教它们:已提交的 `glossary.json`(ADR-012)。没有第二
个需要同步维护的词典文件。

| 术语表条目 | 类型 | 清晰度学到了什么 |
|---|---|---|
| `settle trade` | `verb-phrase` | `settle` 是领域动词;`trade` 是领域名词 |
| `credit tranche` | `noun-phrase` | `credit` 和 `tranche` 都是领域名词 |
| `fx` | `word` | `fx` 是领域名词 |

多词术语按 token 逐个施教,因为标识符本来就是按 token 逐个评分的。所有限界上下
文都会贡献词汇:标识符不携带命名空间,因此评分时无法应用按上下文的作用域。

### 认可的缩写靠声明,而非推断

团队认可的缩写位于自己的根级小节中,该小节会把文件提升到 `schemaVersion: 2`:

```json
{
  "schemaVersion": 2,
  "contexts": { "trading": { "packages": ["Acme.Trading"] } },
  "abbreviations": { "fx": "foreign exchange", "calc": "calculate" },
  "terms": []
}
```

列在其中的 token 不会再被要求拼写出来,而其展开形式正是教学注记用来把它拼写
出来的内容 —— `noun 'fx' (foreign exchange)`。

只有该小节才能认可缩写。仅仅出现在某个已提交术语中的 token(`calc total` 里的
`calc`)会被当作领域名词来教,并且仍然算作缩写,因为没有人决定过它是认可的
缩写。认可一个缩写是有人做出并评审过的决定,而不是一次采集的副作用。

由此得出文件格式的两条规则:

- 该小节**归人类所有** —— 采集永远不会写入它,合并会原样带过它,就像
  `definition` 和 `translations` 一样。
- `2` 这个版本戳**只在小节非空时**才出现,因此从不使用该功能的仓库,写出的仍
  然是与以前逐字节相同的 schema 1 文件。读取方在版本 1 及以上都接受该小节。

### 术语表做不到的事

内置词典保留其权威。项目可以教会评分器一个它们不认识的词;但不能推翻它们已经认
识的词。

- **泛化动词仍然是泛化的。** 提交 `process` 或 `handle` 不会提升它们,布尔前缀
  (`is`、`has`)同理。
- **无意义的占位符仍然无意义。** `temp`、`foo` 之类不会因为被写下来就获得意义。
- **废弃的同义词永远不是词汇表。** 别名的存在就是为了被标记出来;提升它会让它本
  该触发的 `non-canonical-term` 问题失声。
- **`stale` 术语不是词汇表。** 把一个术语标记为 stale,就是在说这个词已经离开了
  该领域。

只有*已提交*的文件才算数。某次运行采集到的内容不会反馈到这同一次运行的评分中 ——
一个会自我膨胀的词汇表会让评分变得不确定且自我认证。提交就是人工批准。

### 适用范围

xUnit fixture、NUnit 套件报告与 `dotnet-narrativetrace clarity-scan` 都用采集所
使用的同一套向上查找来定位术语表(`GlossarySettings.ResolveFile`):
`NARRATIVETRACE_GLOSSARY` 指定显式路径,`off` 会完全关闭该功能,否则采用工作目录
之上最近的 `glossary.json`。

只要存在术语表,读取就是无条件的 —— 它不会改动磁盘上的任何内容。没有
`glossary.json` 的仓库,其评分与该功能出现之前完全一致;而无法读取的术语表会带着
一条控制台提示降级为仅使用内置词典,不会让测试套件失败。

```csharp
var vocabulary = GlossaryVocabulary.FromFile(
    GlossarySettings.ResolveFile(
        Environment.GetEnvironmentVariable, Directory.GetCurrentDirectory()));

var result = ClarityAnalyzer.Analyze(tree, propertyNames, vocabulary);
```

## 报告输出

`ClarityReportRenderer.Render` 会生成跨场景的 Markdown 评分表：

```csharp
var report = ClarityReportRenderer.Render(
[
    new ScenarioClarity("Order placement", orderResult),
    new ScenarioClarity("Legacy processing", legacyResult),
]);
```

## 构建期强制

通过 `dotnet-narrativetrace` CLI(或包装了它的 `NarrativeTrace.MSBuild`
包)，清晰度从建议变成*门禁*。

```bash
# 1. 扫描已构建的程序集，输出到 clarity-results.json：
dotnet-narrativetrace clarity-scan --assembly bin/Release/net10.0/MyApp.dll

# 2. 低于阈值或超出 HIGH 问题预算时让构建失败：
dotnet-narrativetrace clarity-check --results clarity-results.json \
    --min-score 0.80 --max-high-issues 0
```

`clarity-check` 的退出码：`0` 通过(或使用了 `--warn-only`)，`1` 门禁
失败，`2` 用法错误 / 结果文件格式错误。结果文件缺失会被**跳过**(退出码
0)而不是失败 — 这样尚未扫描过的项目不会让 CI 挂掉。

MSBuild 接线(`ClarityScan` / `ClarityCheck` 目标，以及 `ClarityMinScore` /
`ClarityMaxHighIssues` / `ClarityWarnOnly` 属性)详见
[配置指南](配置指南.md#5-msbuild)。

### JSON 契约

`clarity-results.json` 是扫描与门禁之间的契约 — 一个场景对象数组：

```json
[
  {
    "scenario": "OrderService",
    "overall": 0.85,
    "method": 0.90,
    "class": 0.95,
    "parameter": 0.80,
    "structural": 1.00,
    "cohesion": 0.70,
    "issues": [
      {
        "severity": "high",
        "description": "Generic verb 'process' in DataProcessor.process",
        "suggestion": "Use a domain-specific verb"
      }
    ]
  }
]
```

门禁在统计 HIGH 严重级别问题时不区分大小写，因此 `high`(扫描器实际输出
的形式)和 `HIGH` 都被接受。

## NLP 组件

清晰度模块使用手写的 NLP，不依赖任何外部库：

| 组件 | 用途 |
|---|---|
| `IdentifierTokenizer` | 把 `camelCase` / `snake_case` 拆分成 token。 |
| `VerbDictionary` | 对动词分类(`Domain`、`Standard`、`Boolean`、`Generic`、`Unknown`)。 |
| `RoleSuffixDictionary` | 对类名后缀分类(设计模式、功能性、泛化)。 |
| `GenericTokenDetector` | 对 token 的专指程度排序(无意义 → 领域专属)。 |
| `AbbreviationDictionary` | 按层级为缩写评分(通用、广为人知、有歧义)。 |
| `MorphologyAnalyzer` | 通过后缀(`-tion`、`-ize`、`-able`)判断词性。 |
| `CollocationDictionary` | 识别常见的多 token 领域短语。 |
| `CohesionScorer` | 检查方法动词与类角色的一致性。 |
| `MethodNameScorer` / `ClassNameScorer` / `ParameterNameScorer` / `StructuralScorer` | 五个分项评分器。 |
| `DomainVocabulary` | 项目自己的词汇,读自已提交的术语表;在不推翻上述任何词典的前提下扩展它们。 |
