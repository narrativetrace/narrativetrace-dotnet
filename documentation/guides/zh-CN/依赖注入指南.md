# 依赖注入自动包装指南

[English](../dependency-injection.md) | [Español](../es/guia-de-inyeccion-de-dependencias.md) | [Português](../pt-BR/guia-de-injecao-de-dependencias.md) | **简体中文**

本指南介绍 `AddNarrativeTracing` — NarrativeTrace 与
`Microsoft.Extensions.DependencyInjection` 的集成。它会自动包装那些以接口
注册、且实现类命名空间匹配已配置前缀的服务，使这些服务的调用无需改动调用
点即可被追踪。它是 Spring/Micronaut Bean 追踪在 `.NET` 中的等价物：你把它
指向自己的服务命名空间，它就地装饰匹配到的 Bean。

## 包

```xml
<PackageReference Include="NarrativeTrace.DependencyInjection" Version="0.1.2" />
```

## 1. 注册并自动包装

像平常一样注册服务，然后在它们**之后**调用 `AddNarrativeTracing` — 它改写
的是集合中已有的描述符，因此看不到之后才添加的注册。

```csharp
using NarrativeTrace.Core;
using NarrativeTrace.DependencyInjection;

services.AddScoped<IOrderService, DefaultOrderService>();
services.AddScoped<IPaymentGateway, StripePaymentGateway>();

services.AddNarrativeTracing(options => options
    .Namespaces("MyApp.Orders", "MyApp.Payments"));
```

每个匹配到的接口描述符都会被替换为一个新的描述符：它解析出原始实现，并返回
包在其外的 `NarrativeTraceProxy`。该 proxy 把每次调用记录到共享的、DI
scoped 的 `INarrativeContext` 中。

`AddNarrativeTracing` 还会用 `TryAdd` 注册以下内容(因此你先前的注册会
胜出)：

- 一个由 `options.Level` 构建的 singleton `NarrativeTraceConfig`；
- 一个 **scoped** 的 `INarrativeContext`(基于该配置的
  `SyncNarrativeContext`)。

从你执行工作的那个 scope 中自行捕获追踪：

```csharp
using var scope = provider.CreateScope();
scope.ServiceProvider.GetRequiredService<IOrderService>()
    .PlaceOrder("C-1234", "SKU-KB", 2);

var trace = scope.ServiceProvider
    .GetRequiredService<INarrativeContext>()
    .CaptureTrace();
```

## 2. 选项

`AddNarrativeTracing(Action<NarrativeTracingDiOptions>)` 需要一个配置委托。
`NarrativeTracingDiOptions` 暴露：

| 成员 | 类型 | 默认值 | 用途 |
|---|---|---|---|
| `Level` | `TracingLevel` | `Detail` | 共享 scoped 上下文的捕获级别。 |
| `Namespaces(params string[])` | 流式 | (空) | 需要自动包装的基础命名空间。 |
| `ExcludeNamespaces(params string[])` | 流式 | (空) | 要排除的接口命名空间，即使其实现命名空间已被包含。 |

`Namespaces` 与 `ExcludeNamespaces` 是累加的、可链式调用的，且各自返回
选项实例：

```csharp
services.AddNarrativeTracing(options =>
{
    options.Level = TracingLevel.Narrative;
    options
        .Namespaces("MyApp.Orders", "MyApp.Payments")
        .ExcludeNamespaces("MyApp.Payments.Spi");
});
```

如果没有配置任何基础命名空间，就不会匹配到任何东西 — 自动包装严格按命名
空间选择性启用。

## 3. 命名空间匹配语义

这里牵涉两个不同的命名空间，各自适用不同的规则：

- **包含**(`Namespaces`)针对**实现类**的命名空间进行判断 — 也就是具体
  类型的命名空间(参见[第 5 节](#5-实现类命名空间是如何解析的))。
- **排除**(`ExcludeNamespaces`)针对**接口**(服务类型)的命名空间进行
  判断。这样你可以宽泛地包含某个实现命名空间，再把位于另一命名空间的
  框架/SPI 接口剔除出去 — 相当于 Spring 中对 SPI/配置类的排除。

两者都使用相同的**点边界**规则：候选命名空间要么与基础命名空间完全相等，
要么以基础命名空间**加一个点**开头。仅仅共享字符前缀的兄弟命名空间不算
匹配。

以基础命名空间 `MyApp` 为例：

| 候选命名空间 | 是否匹配？ | 原因 |
|---|---|---|
| `MyApp` | 是 | 完全相等 |
| `MyApp.Orders` | 是 | 子命名空间 |
| `MyApp.Orders.Internal` | 是 | 更深层的子命名空间 |
| `MyApp2` | 否 | 兄弟命名空间，没有点边界 |
| `MyAppImpl` | 否 | 共享前缀，没有点边界 |
| `My` | 否 | 比基础命名空间还短 |
| `Other` | 否 | 无关 |
| `null` / `""` | 否 | 未知命名空间永不匹配 |

匹配是**序数比较 / 区分大小写**的，只要匹配上任意一个已配置的基础命名
空间即可。

## 4. 什么会被包装(以及什么不会)

只有**同时**满足以下所有条件，描述符才会被包装：

- **服务类型是接口**(以具体类注册的保持原样)；
- **不是开放泛型**(例如 `IRepository<>`) — `DispatchProxy` 无法包装开放
  泛型；
- **不是 keyed 注册** — keyed 服务会被容忍并保持未包装(不抛异常)，目前
  尚不支持；
- 其**接口命名空间未被** `ExcludeNamespaces` **排除**；
- 其**实现命名空间被** `Namespaces` **包含**。

任何一项检查不通过的注册都会原样保留，因此解析它会得到未经包装的实现。

> **多接口差异。** `DispatchProxy` 每个 proxy 只支持一个接口。一个类如果
> 以两个接口注册(例如 `AddSingleton<IAlpha>(impl)` 和
> `AddSingleton<IBeta>(impl)`)，就会被包装**两次** — 得到两个不同的
> proxy 对象，包着同一个共享目标。这与 Spring/Micronaut 不同，它们会构建
> 一个实现了 Bean 全部接口的单一 proxy。这个差异是有意为之；要在 .NET 中
> 对齐它需要引入 Castle.DynamicProxy。

## 5. 实现类命名空间是如何解析的

包含性检查需要一个具体的命名空间。它按以下顺序获取：

1. 描述符的 `ImplementationType`(按类型注册的服务)；
2. 否则取其 `ImplementationInstance` 的运行时类型(按实例注册的服务)；
3. 否则回退到**服务类型(接口)的命名空间** — 用于按**工厂**注册的服务
   (`AddScoped<IFoo>(sp => …)`)，它们的实现类型在注册时是不透明的。

由于接口与其实现几乎总是放在一起，工厂回退能正确覆盖常见情况；如果你的
工厂返回的类型与接口不在同一命名空间，那么匹配将按接口的命名空间进行。

## 6. 生命周期与作用域行为

- 原注册的**生命周期会被保留**。Singleton 仍是 Singleton(每次解析都返回
  同一个 proxy 实例)，Scoped 服务仍是 Scoped，以此类推。
- 共享的 `INarrativeContext` 是 **Scoped** 的。在同一 DI 作用域内解析出的
  所有被包装服务都记录到**同一个**上下文，因此它们的调用会嵌套成一棵
  追踪树。请按工作单元(每个请求、每个作业)创建作用域，并从该作用域捕获
  追踪。
- 由于上下文是 Scoped 的，而被包装的 **Singleton** 的存活期长于任何作用
  域，Singleton proxy 会在每次调用时通过 service provider 解析当前作用域
  的上下文 — 它不会持有过期的上下文。

## 7. 与 ASP.NET Core 中间件的关系

`NarrativeTrace.AspNetCore` 的中间件与 `AddNarrativeTracing` 的自动包装是
**两条独立的追踪路径** — 不要在同一条请求路径上同时使用：

| | 中间件(`NarrativeTraceMiddleware`) | DI 自动包装(`AddNarrativeTracing`) |
|---|---|---|
| 上下文存放于 | `HttpContext.Items`(按请求) | DI scoped 的 `INarrativeContext` |
| 你如何追踪 | 针对 `HttpContext.GetNarrativeContext()` 做包装 | 从作用域中解析已自动包装的服务 |
| 捕获与导出 | 自动，在中间件的 `finally` 中 | 由你自己调用 `CaptureTrace()` |

**每条请求路径只选其一。** 自动包装的服务记录到 DI scoped 上下文，而不是
`HttpContext.Items`，因此它们**不会**出现在中间件导出的追踪里。如果你想要
中间件那种按请求自动捕获与导出，请改为针对
`HttpContext.GetNarrativeContext()` 包装你的服务(参见
[ASP.NET Core 集成指南](ASP.NET-Core集成指南.md#2-追踪你的服务))。在非
Web 宿主(worker、控制台应用、消息消费者)中，当作用域由你掌控、追踪由你
直接捕获时，才适合使用 DI 自动包装。
